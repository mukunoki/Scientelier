# 内容の改善・探索

- 最初に、成果の価値を左右する不確実性を絞る。実装なら支配的な処理・設計上の制約・精度や保守性、着想なら原理の違い・弱い前提・代替説明・実現可能性を対象にする。承認されていない性能目標・実験・新規性を必須条件に追加しない。
- 主担当は有用なら異なる利用可能なAIへ短い検討を割り当てる。別解を出す担当、ボトルネックを分析する担当、反例と対策を探す担当など、固有の成果を定める。資料集めや完成後の誤り検査だけで代用しない。分担の利益が小さい課題は単独で進める。
- 不確実性のある課題では、序盤から代案と反例など2つの有用な観点を同時に検討することを優先する。課題の入力文だけで考えられる担当は、環境確認や初版実装の完了を前提にしない。inputScope="assignment" の担当は作業ファイル・外部資料を読まず、実行・編集をせず、仮定と未検証を明示する。allowTaskOnlyPeers=true の軽い準備工程と並行できるが、測定・ジョブは排他を維持する。無理に担当数を増やさず、単独の方が良い場合は具体的な費用・効果を説明する。
- 最初の代案は中立な課題・固定入力から独立に考える。その後、通常の依存関係で案を共有し、弱点を補う組合せや判別実験を検討する。盲検の比較案と最終独立レビューへ他担当の結論を渡さない。
- 検討担当は、提案・改善理由・根拠・最小の試し方・費用・弱点を日本語の箇条書きで返す。読み取り専用なら実装や実験は実作業担当へ渡し、許可された分離実装でも共有ファイルやGPU等の競合を避ける。CLIを直接起動しない。
- 主担当は候補を同じ条件で比較し、有望な変更を実際に試す。要求に応じた計測・反証・小例を用い、改善前後と副作用を確認する。性能評価はfair-benchmark、仮説の判別はhypothesis-designを必要なときだけ読む。変更不要・全案棄却も有効な判断であり、改善を創作しない。
- 初回の成果・原稿ができた後、仕上げ前に一度、説明不足と改善余地をまとめて点検する。読者が対象・表現・仮定・手順・結果の理由を本文だけで理解できるか、意味のある改善案を試して比較したかを確認する。別AIの指摘は現物で確認し、主担当が同じゴール・ラウンドで修正・試行と終了判断を行う。利用可能な別AIや担当枠がなければ自己点検と明示し、独立確認済みとは扱わない。
- 終了判断は既存のwork-checkのcontentDecisionへ短く記録する。explanationには説明不足を確認・修正した根拠、improvementには案の試行・比較・採否または追加試行が不適切な理由を書く。finishは自身の作業を仕上げへ渡す判断で、全体合格ではない。continueはneeds-workと具体的なremainingWorkへ返し、既存の試行上限内で扱う。未達・未確認を隠さず、無制限に探索・点検を繰り返さない。管理情報は本文・付録へ書かない。
- 結果に応じて、検討すべき次の不確実性があれば残り時間・使用枠に見合う短い反復を計画する。必須事項を先に終え、費用に見合う有望な変更がなければ追加探索を区切る。固定の案数・反復数や管理書類を増やさず、採用／不採用／保留・理由・検証根拠は既存の作業報告へ残す。
- 初期の検討と実作業を主工程にし、TeXは内容のメモとして更新する。体裁・文体の仕上げと最終PDF確認はレポーターにまとめる。版が変わらない機械検査は再利用するが、必要な独立検証・文献照合・最終PDF確認は省略しない。提案が出たことや検査件数だけを内容の洗練の証拠にしない。
