# Scientelier 操作・実行仕様ガイド

複数AIによる研究開発ワークスペース。旧名称はAgent Harnessです。

インストールは[インストール手順](installation.md)、開発・保守は[コード構成と変更時の注意点](architecture.md)。旧保存版の互換経路も含むガイドです。新規タスクの標準は現在の画面とプリセットを参照してください。

### 研究内容を深めるための実行方針

- **品質と速さを優先**します。総トークン数は観測用であり、計画・担当・改良の起動制限には使いません。実際のサービス使用枠、認証、同時実行数、安全な作業分離は引き続き確認します。
- **能力を考慮して主担当を選び、継続**させます。設定された担当を優先し、未指定ならモデル能力の参考指標とサービスの品質優先値を使用します。参考値がないモデルを低能力とは扱いません。使用枠・認証などで使えない場合は既存の引継ぎ方式で交代します。
- **他AIへの委任は具体的な利益で判断**します。実装・最適化・分析、独立案、早期の反証・レビューを通じて、時間短縮、使用枠分散、発想拡大、品質向上を狙います。担当数や使用率を均等にすること自体は目的にしません。
- 新規の研究モードは、着想・調査・実装評価・執筆を必要に応じて往復する**主担当の研究ループ**です。各モードの保存版ルールは方法として使い、四つの直列引継ぎを強制しません。
- 新規の研究・論文モードは**一つの論文TeX/PDF**に統合します。「作業報告」は提案、実施、結果、解釈、次の方針が中心です。問題・検証上の留保は補足へ分けますが、結果を無効にする欠陥は結果と一緒に示します。

保存済みタスクの工程、承認条件、複数文書、編集済みルールは自動で書き換えません。新しい統合方式を使う場合は新規タスクを作成してください。既存タスクの追加作業は保存された構成を引き継ぎます。数値・文献・PDFの検証、独立レビュー、反復回数上限は維持し、未確認を合格にはしません。改善の実効性は、実タスクの中核成果までの時間、有益な委任、修復と再測定の記録で確認します。

### Macで起動する

デスクトップの **Scientelier.app** をダブルクリックします。ターミナルを開く必要はありません。Dockに追加して使うこともできます。起動中にもう一度開くと既存の画面が前面に出ます。設定・タスク・ログイン情報は従来と同じ場所を使用します。

配布版 `.app` はElectron・実行コード・標準skills／執筆ルールを含み、元のソースフォルダに依存しません。開発用の `npm run app:mac -- --install-desktop` は、従来どおり開発フォルダの最新版を読むランチャーです。開発用と配布用を区別してください。`現行版を起動.command` と `npm start` はソースからの起動に利用できます。

画面・アプリ・リポジトリの名称はScientelierに統一しています。既存データと暗号化キーを継続利用するため、内部の保存フォルダ名 `agent-harness`、Macのbundle identifier、MCPの `agent_harness` 名、既定の `Agent Harness Reports` は変更しません。名称変更でタスク・成果物・保存済みのルールを移動したり、再ログインを要求したりする処理はありません。

### Gitで管理する

このプロジェクトはローカルGitの `main` ブランチで管理します。ソース、テスト、スキル・テンプレート、設計資料、依存関係の定義を記録します。認証・タスクデータ、生成したアプリ、依存ライブラリ、ログ・検証出力、旧版のスナップショット、別用途の実験ディレクトリは記録しません。除外はファイルを削除する操作ではなく、既存データはそのまま残ります。

変更確認は `git status` / `git diff`、保存は必要なファイルを `git add` して `git commit` で行います。開発を担当するエージェントは、[プロジェクトの作業ルール](../AGENTS.md)に従い、検証後にその作業の変更をcommit・pushまで行います。これはScientelier自体の開発時の運用であり、アプリ内のタスクが自動でpushする機能ではありません。公開前の確認と履歴なしの書き出しは[公開手順](publication.md)を参照してください。認証情報・タスクデータ・ログはコミットしないでください。

### 長時間化・重複確認を抑える実行戦略

主担当には、実装・実験・文献照合・PDF仕上げを一つの長い作業へ詰め込まず、目安時間の1/3程度で中核成果を確認できる作業単位を計画するよう指示します。計画内の作業中には、実作業時間の1/3・2/3を契機とする短い統括判断を追加できます。既存の最大3回の判断枠を使い、未着手の仕事だけを補足します。計測中や並列枠が埋まっている場合は安全な区切りまで待ち、現在の担当を強制終了しません。

統括判断には目的・計画・結果の短い要約だけを渡し、全文指示や履歴の再取得を要求しません。統括判断の観測不能な使用量には1回3,000 tokensの推定値を使い、実測できた使用量はそのまま計上します。推定値は実際の消費量でも起動制限でもありません。

一次資料は、書込担当がURL・公開版・ハッシュを付けた同じ資料を用意し、異系統AIが結論を見せず並列に照合する方針です。単に異なるAIにするための直列依存は不要です。取得不能の同じURLへの反復は抑え、未確認を残して他の必要作業を進めます。この資料準備・再試行方針は担当への指示であり、ハーネスが自動取得を保証する機能ではありません。

Codex・Claude・OpenCodeの取得可能な実モデル情報を、その実行のネイティブ記録から保存します。`get_run_evidence`では指示取得後にモデル・取得スキルの管理情報だけを参照でき、他担当の結論やログは渡しません。実モデルの情報が工程終了時に揃う場合は統合時に確認し、管理情報の不足だけで文献・実験を繰り返さないよう指示します。不明なモデルを既知扱いせず、管理記録は内容の正しさやサーバーの身元証明とは区別します。

品質台帳の`recheck`は、有効な結果と、変更された入力・検査方法・依存先を示します。同じ記録の再提出は後続検査を無効にしませんが、実際の変更は依存先まで再確認します。最終PDFの確認と独立レビューは維持します。通常の自動割当では実作業時間のサービス偏りも弱い判断材料にし、明示した担当・モデル条件・使用枠・文脈再利用の利益を優先します。

ネイティブのAPI混雑・認証失効・接続エラーを確認した場合は、前のCLIの終了・実行ロック解除を確認後、同じ未完了工程を条件に合う別CLIへ引き継ぎます。アカウントの使用枠超過とは別に扱い、混雑で使用率やリセット日時を変更しません。停止を確認できない場合、または条件に合うCLIがない場合は、安全のため自動引き継ぎを保留します。

### 必須の実行条件を確認できない場合

実作業担当は、長い実装・測定の前に、自身のCLIセッションで必要なツール・権限・対象デバイスを最小確認します。必須機能が利用できず通常の限定的修復でも直せない場合は、専用の環境障害として停止します。同じ失敗を再作業で繰り返したり、未実行のままレポート・レビューへ進んだりしません。任意機能の失敗や通常のテスト不合格とは区別します。環境確認は担当からの報告に基づき、ハードウェアや成果の合格をアプリが推測するものではありません。

ローカルCodexの書き込み工程では、サンドボックス設定と必須のGit記録が両立しない場合に起動前に停止します。権限は自動で変更しません。画面の短い原因・復旧方法を確認し、環境を直して「中断した工程から再開」を押すと、完了済みの工程と成果を保持して必要な確認をやり直します。並行実行中の担当は終了を待ち、新規割当は停止します。

### 時間目安・並列実績・工程の見える化

「実行 → 工程・担当」は依存グラフ／実績タイムラインを切り替えられます。矢印は保存された前提関係で、同時実行の証明ではありません。タイムラインは実際の起動・指示取得・終了時刻を表示し、起動／指示待ちは斜線、時間区分が不明な旧記録は灰色です。ノードから担当の指示・残課題・端末を開けます。現在／上限／最大実績の並列数、2担当以上が重なった時間も表示します。

Codex・Claude・OpenCodeは最初の指示取得を実作業開始として記録し、それ以前を経過時間から除外します。旧ログにハーネスの指示取得イベントがある場合だけ復元します。根拠がない記録や取得後のCLI内部の承認待ちは判別できず、「区分不明」または実作業時間に含まれる場合があります。並列時間は重複加算しません。

目安時間のある計画は、依存関係・同時実行上限・共有領域への排他的書込みを考慮して見積もり、レポート／レビュー時間を予約します。未見積りを0分と断定しません。見積りと体制の検討が不足する超過見込みの初期計画は、一度だけ再配分を依頼します。全工程を見積り、クリティカルパス・並列効果・文脈・リソース配分を説明済みの計画は、目安超過だけで再提出させず進みます。必須条件を緩めたり、時間だけでCLIを強制終了したりしません。各担当には工程の区切り／3〜5実作業分ごとの `get_progress` 呼出しを指示します。時間情報は15秒間隔で更新しますが、LLMへの定期呼出しは行いません。

序盤は、実機不要の代案・反例検討を環境確認の後ろに一律に並べず、利用可能な異系統AIでの同時検討を計画します。`investigation` の `inputScope:"assignment"` は指示本文と保存版スキルだけを入力とし、作業ファイル・ログ・外部資料の取得、コマンド実行、編集は禁止です。別の制御用ディレクトリで起動し、作業／品質／研究台帳の管理ツールは配布しません。これは指示・入力の分離であり、OSサンドボックスではありません。軽い環境確認等の `primary-work` が `allowTaskOnlyPeers:true` を明示した場合だけ、これらの検討を同時に実行できます。通常の作業ファイル読取、共有編集、性能測定・資源を共有するジョブは排他を維持します。追加のユーザー設定は不要です。必要な前提・利用可能なモデル・使用枠を守り、有益な分担がない場合は直列を選べます。

同じ固定資料に対する並列の独立照合では `requirements.independenceGroup` と互いに重ならない `modelFamilies` を指定できます。既存のモデル制約を守り、比較相手の完了を待たずに実行可能です。モデル実体の確認・証拠の独立検証は引き続き必要です。従来の `independentFrom` による逐次照合も保持します。保存済み計画の依存関係を自動で書き換えることはありません。

### 独立案を並行実行して比較・選択

主担当は、通常の分担に加えて「同じ問題、または不確実な一部分を2〜3担当が独立に解く」計画を選べます。常に重複実行するのではなく、品質・時間短縮の期待と、比較統合・仕上げの時間やサービス使用枠を比較して判断します。上限並列数・使用枠・既存の権限は変更しません。

計画の各候補に `comparison: {input, evaluation, approach}` を付け、固定した共通入力・評価基準と、候補ごとの異なる解法を指定します。同じ `requirements.independenceGroup` と、互いに重ならない利用可能な `modelFamilies` を使います。入力・評価・達成条件・前提工程は候補間で一致させ、候補同士を依存させません。新規会話で開始し、同僚の結論・ログ・判断メモは自動配布しません。これは指示とコンテキストの分離であり、OSの読取アクセス制御を追加するものではありません。

主担当の比較工程は全候補を待ち、同じ条件で証拠を検査します。比較表・採用理由・不採用理由を作業報告に残し、良い案の採用、部分統合、全案不採用を判断します。統合後は再検証し、最終独立レビューも維持します。先に終了しただけで勝者とせず、他候補を自動強制終了しません。候補を使う後続工程は、全候補に依存する `primary-work` の比較工程を経由するか、末尾の主担当統合で処理します。

全モードで読取専用の設計・解法・説明案を比較できます。一般コーディング工程と、保存されたモード範囲が実験的な着想探索を認める工程では、許可された分離作業ツリーで独立プロトタイプも比較できます。旧式の読取専用アイディア設定、論文執筆・調査専用工程に実装権限は追加しません。所有ファイルは `variants/a/...` と `variants/b/...` のように分け、同じ本番ファイルを同時編集しません。未採用案は理由付きで除外し、ファイルを保持します。HPCの数値検証・作業解除の権限を迂回しないため、HPCではまず読取専用の案比較を行い、選択後は従来の検証付き実装工程を使います。稼働中の計画を自動置換せず、新しい主担当計画から適用します。

### 担当間の短い相談

主担当と分担担当の知見共有に加え、計画で `communication: {with:["担当キー"],purpose:"具体的な論点"}` を設定した担当間が相談できます。新しい計画から適用し、既存タスクの計画・担当を自動変更しません。独立レビュー・独立案・反証担当には相談ツールを配布しません。

相談は担当ごと12通、1論点2往復、1通1500文字までです。既存の接続を共有し、会話だけで新しいCLIを起動しません。未起動の主担当への知見は開始後に届き、旧ラウンド・旧ゴール・旧計画へ誤配信しません。「履歴 → 担当間の相談」で質問・回答・配信状態を確認できます。受信文は未検証の参考情報であり、証拠・承認・合格判定は別です。返答待ちや頻繁なポーリングで実作業を止めない方針です。

### 遠隔端末の保持（tmux）

遠隔の端末保持方式は「システム設定 → 遠隔システム → 端末保持」で指定します。標準は「自動（tmux優先）」で、未導入なら直接端末に戻ります。tmux必須を選んで未導入なら、CLIを起動せず準備を求めます。最終マシン側のtmuxを事前に用意し、ログインノード上の常駐が施設の規則で認められるか確認してください。切断中も現在のCLIは作業を続けますが、次の工程・メッセージ中継・負荷分散はMac側が再接続するまで進みません。サーバー再起動・CLIクラッシュまで復元する仕組みではありません。画面出力は遠隔の実行管理フォルダに0600の `terminal.raw.log` として保持します。

### CLIの初回フォルダ確認

使用候補を途中から起動しても、ハーネス所有の各工程ではCLIの自動承認設定を毎回適用します。Codexはその起動の作業フォルダだけをtrustedに指定し、保存済みのサンドボックス設定は維持します。Antigravityは `--dangerously-skip-permissions`、OpenCodeは `--auto` を使います。OpenCodeの明示的なdenyは解除しません。認証用・ユーザー操作用の端末にはこの自動承認を付けません。

Claude Codeの `bypassPermissions` とAntigravityの `--dangerously-skip-permissions` は、対話起動時のフォルダ信頼確認とは別です。両CLIについて、起動直後の既知の確認画面で実際の起動フォルダとの完全一致を確認してYesを選択します。選択肢の順序・番号と文言の折り返しを考慮し、CLIの初期入力ガードが解除されるまで画面の安定を待ちます。長いパスの改行位置は推測せず、端末を一度だけ広げて完全なパスを再確認します。小さいペインでは起動確認中だけ端末サイズを確保し、確認後はユーザーの最新のサイズに戻します。選択後の再描画を確認してからEnterを一度だけ送り、手入力・指示取得・終了で自動応答を解除します。承認操作は実行ログに残り、信頼状態の保存はCLI自身に任せます。フォルダ内の設定・フックも信頼対象になるため、専用プロジェクトで利用してください。別フォルダ、プロジェクトが追加の権限を宣言する画面、未知の画面、ログイン、OSのファイルアクセス権限は自動承認しません。認識できない初回確認には端末上に手動回答の案内を表示します。共有の設定・認証ファイルは直接書き換えません。

### ローカルCodexの権限とGPUアクセス

ユーザー指定により、新規ローカルタスクのCodexは **Full accessが標準** です。作成時に権限をタスクへ保存し、ゴール設定・実装・レビューを含む各起動に適用します。停止中のタスクの「作業場所・実行設定 → ローカルCodexの権限…」でサンドボックスへ戻せます。既存タスクは設定を保持し、古い未指定値はサンドボックスのままです。遠隔プロファイルの権限をローカル実行へ流用しません。

「引き継ぎ」「最初からやり直し」で作るローカルタスクも、元の権限が未指定ならFull accessを保存します。明示的なサンドボックス設定は引き継ぎ、元のタスク自体や遠隔タスクの権限は変更しません。

ローカル担当の指示には、担当CLI内での実行環境の事前確認を含めます。必要なコンパイラ・SDK、GPUのデバイス取得と最小実行、書き込み担当のGit利用可否を区別して確認し、権限拒否を未導入と誤認しないようにします。これはエージェントへの必須指示であり、ホスト側で自動的にGPU実験を走らせる機能ではありません。権限変更後は再確認し、実装の精度・性能や文献・PDFレビューは別途必要です。

権限の変更後は新規会話で成果物から引き継ぎ、保存だけでは実行しません。Full accessはGPU専用の許可ではなく、作業フォルダ外も通常ユーザー権限で操作可能です。読取担当にもOSの書込制限がなくなるため、信頼できるタスクだけで利用してください。コンパイラ/SDKの不足や管理者ポリシーは解除しません。他CLIや通常のターミナルで使うCodexのグローバル設定は変更しません。

中断工程があるローカルタスクでは、同じ権限画面の「保存して同じ工程から再開」で保存と再開を続けて行えます。保存に失敗した場合は起動せず、再開だけ失敗した場合は保存済みの権限と復旧方法を表示します。完了済みの工程・成果・ゴールは保持し、必要な環境確認は再実行します。権限の保存はレポートの同期や別タスクの終了を必要としませんが、このタスクに残ったCLI端末は事前に終了してください。

### タスクのGit管理（必須）

全モードで、ゴール承認後の開始・再開時にGit作業ツリーを必須確認します。未管理のタスクフォルダは初期化し、既存リポジトリやworktreeは再利用します。遠隔側は確立済みSSHの最終作業場所で確認します。Git未導入や既存リポジトリの異常は理由を表示して開始を止めます。既存タスクにも次回開始・再開から適用します。

各書込担当には、変更前の状態確認、安全に分離できるソースの基準コミット、検証済みの作業単位でのコミット、引き継ぎでのコミットID・未コミット理由の報告を必須指示として渡します。コミット内容の妥当性は独立レビューでも確認します（Git初期化の機械確認と、担当による変更内容・コミットの確認は別です）。読み取り担当は変更せず、HPC分離作業はHEADを保持して主担当が統合後にコミットします。別フォルダのレポート原稿は、そのフォルダのGitで管理します。

アプリは既存ファイルの一括追加・コミット、ユーザーのステージ解除、著者名の創作、グローバル設定の変更、push、履歴の書換えを行いません。秘密情報・大容量データ・生成物はコミットせず、ソースと再現情報を追跡します。`.git`はレポート転送・スナップショットに含めず、各ホストの履歴を保持します。

### 実行途中での戦略変更

タスクの「Goal → 実行戦略を設定」から、実行中でも並列数・割当方針・会話引継ぎなどを保存できます。「適用中」と「変更予約」を分けて表示し、予約は取り消せます。現在の担当（並列なら全員）と結果確認を終え、次の担当を起動する前に反映します。端末の強制終了や、処理中の計画に新しい上限を遡及適用することはありません。予約は一時停止・アプリ再起動をまたいで保持します。

既存計画の依存関係や完了済み成果は保持します。最大分担数・分担ON/OFFは次の計画に適用し、必要な残作業の見直しは主担当が判断します。並列数を増やしても依存する作業や共有ファイルの編集は並列化しません。レビュー方式は実行中またはレビュー開始後には変更できません。新規タスクのシステム既定値は既存タスクへ自動反映せず、遠隔タスクの初期並列数1も明示的に変更するまで維持します。

通常・効率重視のどちらでも、許可済みで利用可能な全CLIを調査分担の候補にします。通常設定だけCodex/Claudeに限定することはありません。使用枠・同時負荷・能力参考・会話引継ぎの利点で選び、明示した担当やモデル系統・独立性・必須スキルの条件は維持します。

利用可能なCLIがなくなった場合は、実作業の失敗とは区別して「起動待機」にします。分担と成果物を取り下げたり、再計画回数を消費したりしません。Resourcesで接続・ログイン・使用枠・利用サービスを確認し、同じ工程から再開します。並列担当の一つが実作業に失敗し、別担当が起動できなくなった場合も、まず起動条件を復旧してから残作業を判断します。

### 独立照合の割当と配置の修復

計画の各作業に `requirements` を指定すると、モデル系統・独立性・必須スキルを起動前に検査します。例えば担当Bに `{"modelFamilies":["gemini","deepseek"],"independentFrom":["a"],"skills":[{"id":"writing-rules","revision":"保存された64桁のSHA256"}]}` を指定し、`dependsOn:["a"]` でAを先に完了させます。CLIや契約先が違うだけでは独立とせず、明示的なモデルIDの系統を比較します。自動選択など系統不明の設定は不合格です。実際のバックエンドの同一性まで保証するものではないため、担当自身にも起動時のモデル確認を要求します。

読取専用の調査担当にも執筆ルールを配布します。指定版は同じ承認ゴールの実行履歴から取り出し、現在のルールへ自動置換しません。独立照合では比較対象の結論・ログを引き渡さず、中立な証拠・一次ソースから検証させます。配置・スキル条件を満たせない場合は起動前に担当を残して停止し、同系統への切替や再計画による再投入は行いません。

旧計画で失敗して履歴へ移った調査担当は、停止中タスクの「担当・スキルの配置を修復…」で最新計画から復旧できます。比較対象・許可するモデル系統・必要な文献検証スキルを選びます。成功済み担当、ゴール、成果物、予算を保持し、修復担当と後続の統合・報告・レビューだけを再開待ちにします。保存だけでは実行せず、通常の「中断した工程から再開」で接続・使用枠を確認します。作業権限や範囲の承認を迂回する機能ではありません。

### 全モード共通の品質・検証

更新後に作成し、ゴールを承認したタスクに適用します。タスク内の「品質・検証」で、通常は未確認・不合格だけを表示し、合格済みの検査はチェックで展開できます。既存タスクには完了条件を後付けしません。

共通部分は、検査計画・実施結果・証拠ファイルの指紋・依存関係・担当への差し戻しです。主担当は計画時から定型検査をスクリプト化し、対象ファイルと方法を `quality_manage` に登録します。正常例と異常例で検査自体を確認し、対象ゼロ・未照合ありを合格にしません。意味の理解が必要な検査は根拠を残して判断します。変更された対象・計画・依存結果は再検証し、無関係な合格済みの作業は再利用します。

モード別の確認項目は、アイディア＝候補比較と予備検証、関連研究調査＝探索範囲と原典、コーディング＝要件・異常系と回帰、論文＝主張・証拠・論旨、ポスター＝中心メッセージと省略の妥当性です。研究モードは各段階の項目を継承し、研究・HPC専用の台帳は重複させず参照します。文書全般ではPDF・数値図表・引用を確認し、ポスターやスライドも実寸・読む順序・はみ出しを確認します。細かな方法は既存の編集可能なモード規約・執筆ルール・スキルから受け取ります。

文書の不備はレポーターへ、実装・データ不足はワーカーへ、既存の修正回数・使用枠の範囲で戻します。条件付き対象外には根拠が必要で、承認済みゴールの必須条件は免除できません。品質台帳は最終独立レビューの代わりではなく、スクリプトの実行真正性や意味内容の正しさは別CLIのレビューでも確認します。

実作業と文書の台帳はそれぞれのルート内の `.agent-harness/<task ID>/quality/<work|report>/ledger.json` に保存します。遠隔作業とMacの文書生成は別領域として扱い、文書転送では管理台帳を混入させません。証拠は通常ファイルで、1ファイル32MB以下です。大きなデータは検証可能な分割データ・索引を用意します。チェック記録は報告書本文へ転載しません。

### 証拠付き研究サイクル（ScientistTwoを参考にした拡張）

新規の「研究モード」・主担当方式で有効です。タスク内の「候補・実験・証拠」で、固定した評価条件、派生候補、実験と別CLIの批評、採用結果、証拠の変更を確認できます。既存タスクには遡及適用しません。

主担当は `research_manage` で評価条件を先に固定し、基準実験 → 小規模評価 → 独立批評 → 全体評価 → 要素比較を計画します。批評担当は `kind: investigation, researchCritic: true` として実験担当への依存を明示します。数値上の改善だけで成功とはせず、証拠・批評が不足した場合は既存の修正ループへ戻します。許可された探索で改善を確認できないときは否定的結果を報告できますが、ゴール達成とは別判定です。

研究台帳は作業場所の `.agent-harness/<task ID>/research/ledger.json` に保存し、遠隔でも同じエンジンを使います。実験記録ごとに不変のコード・測定・実行環境の証拠を残してください。変更は依存する判定も無効にします。再実行はまず `snapshot` を読み、同じIDを再登録しません。固定条件を変更する場合は新規タスクが必要です。

採用時は検証済みの全候補と比較し、他候補に全指標で劣る選択は拒否します。過去の成功証拠が失効した場合も履歴を無視せず、保存した証拠の復元・再検証を要求します。復元できない場合は未検証のまま保持し、新しい条件での検証は新規タスクで行います。通常の中断再開は同じ台帳を使いますが、「引き継いでやり直す」は新しいタスクIDのため台帳も新規です。成果物は再利用できますが、評価条件・実験の再登録と独立批評の再取得が必要です。

原論文との差分：全体評価の数値比較は原著の公表SOTA値ではなく、固定条件で再現した `baseline-full` を使います。探索は台帳全体の `maxExperiments` と既存の反復回数・実際のサービス使用枠で制限し、候補ごとの専用Engineer回数制限は設けません。批評担当のルーティングでは各依存経路の直近の実験担当を除外し、過去の別工程までは除外しません。批評操作では対象実験ごとに別CLI・別実行単位であることを再確認します。批評パッケージの作成は主担当の計画責任であり、未提出の批評を自動合格させません。

追加指摘と反論実験・原典検証・改稿の対応付けは担当への必須指示と独立レビューで確認します（意味内容を機械的に保証する機構ではありません）。差戻しでは各モードの担当が関連する指摘だけを扱い、既に合格した成果物を再利用しますが、各工程の再確認セッションには費用がかかります。進展判定は必須条件の新規合格に加え、未解決指摘の集合が縮小し、合格条件に紐付く証拠のハッシュが更新された場合を考慮します。これは反復打切りの補助判定であり、最終合格には従来どおり独立レビューが必要です。

工程の完了確認・「残作業あり」の差戻し・最終確認・手動の完了操作では、適用される品質／研究／HPC検証の不足を一度に収集します。台帳を読めない場合も合格扱いにせず、他の検査結果と併記します。ユーザー判断が必要な `ask-user` は変更しません。最終確認で全体タスクを完了できない場合も、その回の作業履歴と成果物は保持します。

初版は数値比較可能な実験研究向けです。台帳は提出された証拠の整合を検査するもので、実験実行の真正性・学術的新規性・ツール外の計算量を保証しません。論文と同等の研究能力の実証、専用の木探索アルゴリズム、専用メタ査読器は含みません。詳細は[設計分析（TeX）](scientist-two-design.tex)を参照してください。

複数のAI CLIを、一つのタスクに対するチームとして運用するmacOS向けElectronプロトタイプです。

CLI・モデル・認証・使用率・アカウント区分はResourcesだけで管理します。システム設定にはこれらの編集欄を置きません。Resourcesの「作業環境」でこのMac・遠隔を絞り込み、各CLIの「接続・CLI端末」でSSH接続・ログイン・診断まで行えます。システム設定の遠隔システムは接続先の登録・編集専用です。モデル・利用率の既定設定は全環境共通で、接続・認証の状態は環境別です。

遠隔は「SSH接続」→最終マシンで環境設定とcd→「ここを作業環境として確定」→「CLIを開く」または「ログイン・更新」の順です。踏み台を含む準備済み接続を共有し、CLIごとに独立した対話端末を作ります。Codexの遠隔再ログインはデバイス認証、Claudeは公式ログイン操作、OpenCodeは保存した接続先の認証（Ollamaアプリ経由では遠隔の `ollama signin`）です。認証内容はCLIが保持し、端末本文を作業ログへ保存しません。「画面を閉じる」は表示だけを閉じ、「CLI端末を終了」「SSHを切断」は明示的な別操作です。CLI端末が残る間のSSH切断は拒否します。タスク実行中の同一CLIへの認証変更も拒否します。次の担当は同じ環境・認証を使う新しい会話で開始し、ログイン端末の会話は引き継ぎません。

「認証・使用枠を更新」は接続済み環境で読み取り専用の確認を行い、新規SSH接続やモデル生成はしません。Codex/Claudeは遠隔側で使用枠を取得し、解析済みの統計だけを持ち帰ります。接続済み環境の定期更新も行い、更新失敗時は前回値と失敗理由を保持します。Antigravity/OpenCodeの遠隔使用枠の自動取得は未対応と明示し、同一契約を明示的に紐付けたローカル観測値があれば共通のアカウント欄で確認できます。

CLI検出、認証確認、モデル通信、使用枠は別の事実です。認証報告は5分、使用枠は15分を過ぎると前回値／再確認扱いです。残量取得が未対応でも認証済みとは区別し、未取得を0%・利用枠十分とは表示しません。「認証確認済み」はモデル利用権や実行成功の保証ではありません。診断は選択したCLIに対して実施し、Codex固有の隔離検査はサンドボックス指定時だけ行います。

自動割当では、使用量の未取得に架空の50%消費を付けず、実際の使用率と情報の不確かさを別々に評価します。Ollama経由のOpenCodeも、Web残量表示が未連携という理由だけで過度に不利にはしません。確認済みの使用制限・認証障害・モデル指定・独立レビュー条件は維持します。このMacの「CLIを開く」では、選択中のモデルと既存のOllama認証を使う対話端末を開けます。画面を閉じても端末は保持し、終了は「端末を終了」で行います。

Usageは契約アカウントの観測値です。「アカウントを区分」で、同じ契約を使うローカル・遠隔に同じ表示名を設定すると、使用率を合算せず最新の観測値を1つ表示します。取得元・時刻と環境ごとの認証エラーは保持します。アカウントの一致はユーザー確認であり自動検証ではありません。空欄は未区分として別々に表示します。この区分は表示専用で、認証情報の共有・転送、既存の環境別ルーティング／制限判定は変更しません。設定はいつでも空欄に戻せます。

### 使用枠超過時の自動引き継ぎ

使用枠超過の通知を受けた工程は完了扱いにせず、同じ作業ディレクトリ・工程のまま利用可能な別AIへ自動で再割当します。部分成果・ログ・未解決事項は保持し、次の担当には既存ファイルと実行中のバッチジョブを確認して残作業を続けるよう指示します。完了済みの前工程は繰り返しません。

Antigravityの `Individual quota reached` は、CLIが終了せず完了通知も出せない場合でも、リセット時間・Error IDを伴う標準エラー画面から検出します。CLIの明示的な `rate-limited` 通知と、終了時の明確なプロバイダーエラーにも対応します。単に指示・ログに「rate limit」「429」が含まれるだけでは実行中のCLIを止めません。

切替前に使用枠不足となったCLIの停止を確認します。SSH実行では今回の担当だけに停止を要求し、遠隔側の終了記録と実行ロック解除を確認してから代替を起動します。SSH接続や投入済みバッチジョブを一括終了しません。停止確認に失敗した場合は二重実行を避けて保留します。

終了通知が届かない場合は、再開時・担当交代時に遠隔側の記録とPIDを自動確認します。終了済みと確認できる場合だけ、その担当の古いロックを解除して続行します。起動ロックに阻まれてCLIを起動できなかった場合も、作業成功とは別に「未起動」と記録し、存在しないCLIの終了待ちにしません。旧版の未起動記録は、保存された厳密な起動失敗ログ・保存済み最終ホストの一致・ロック消滅・Linuxの対象プロセス不在を確認できる場合だけ自動復旧します。認証の再入力、SSH再接続、識別できない残存処理は手動対応が必要です。読み取り専用クロスレビューは担当別ロックで並列実行し、書き込み担当は従来の排他制御を維持します。

停止確認や認証で詰まった場合は、タスクを一時停止して、Executionの各端末にある「CLIを復旧…」を開きます。遠隔の場合は先に「実行環境を復旧…」で保存済みの接続先へ接続してください。専用の対話シェルで表示されたCLIコマンドを実行し、認証・正常応答を確認します。旧CLIが残っていれば表示されたPIDを確認して手動で終了します。CLIとシェルを `exit` で終了し、正常応答の確認にチェックして「確認してReadyにする」を押します。古い実行で終了記録がない場合だけ、旧CLI・子処理の終了についても明示的な手動確認が必要です。

Readyは「次の割り当てで利用できる候補」であり、作業の完了や使用枠の復活ではありません。元の作業・成果物・レビュー条件は保持し、自動再開はしません。「中断した工程から再開」で続けてください。復旧中は同じ作業フォルダの実行と同じサービスへの新規割り当てを抑止します。復旧端末には作業用MCPや完了フックを渡さず、出力を外部ログへ保存しません。OpenCodeは設定済みの接続先・モデルを使います。

超過した契約はリセット時刻（未取得なら15分）まで候補から除外します。部分的な使用量更新やアプリ再起動でこの待機を解除せず、ローカル・遠隔の契約枠は分離します。許可されたCLI・明示した担当固定・モデル系統の独立性・レビューの提供元・保存済みスキル版は維持します。これらを満たす代替がなければ、要件を緩和せず停止理由を表示します。

失敗・中断した最新の端末には「別CLIへ引き継いで再開…」を表示します。タスクを停止した状態で代替CLIを選ぶと、旧CLIの終了確認後、成果物・ログ・完了済み工程を保持して同じ工程を再実行します。指定はその工程の次の起動だけに適用し、システム全体の担当設定は変更しません。利用できない候補には接続・使用枠・独立性などの理由を表示します。クロスレビューのサービス変更は、未完了の2段階を一組として、まだ参加していないサービスへ変更できる場合に限ります。既に他のCLIが引き継いだ履歴や完了済み工程から重複起動することはできません。

独立レビューで1サービスが失敗し、他の2サービス以上が有効な独立判定を提出済みの場合は、同じ画面の「残るサービスで相互レビューを続行」を使えます。失敗サービスの未受理の2枠を履歴へ移し、残る各サービスが他社の判定を検証するよう依存関係を再編します。成果物の証拠・旧CLI終了・残るCLIの使用枠を確認してから適用し、提出済み判定や指摘のある担当の除外、1サービスへの縮小、クロスレビュー開始後の枠削除は認めません。失敗の部分記録も未検証情報として後続に渡し、失敗を合格として数えません。

## 必要時に読む作業スキル

計画時に使用するスキルIDと適用工程を、既存の `summary` または `coordination.contextPlan` に記します。新しいJSONキーや完了条件は追加しません。仮説設計、原因切り分け、公正評価、変更影響、判断記憶、再現性、自作スキルの試験を担当・作業内容に応じて選びます。

Codex / Claude / OpenCodeは `get_instructions` の後に `get_skill` で必要な本文を取得します。Antigravityはカタログが示す実行専用ファイルを読みます。ローカル・SSHとも実行ごとの保存版を渡し、執筆ルールの版と既存の検証条件は維持します。確認用の指示書TXTには引き続き全文を表示します。

取得を観測できた場合、Executionの「実行計画・体制」の工程詳細と外部ログに、スキルID・内容ハッシュ・回数・本文の推定量を表示します。これは適用済みの証明でも課金実測でもありません。本文の取得分を予算・文脈の推定に算入します。記録未取得は未使用やゼロ消費を意味しません。Antigravityの通常ファイル読取は観測できないため、提示した全本文を保守的に推定へ含めます。キャッシュ・内部ツール・実課金の完全な計測や厳密な予算上限は保証しません。

会話切替の目安tokensと、引き継ぎ要約の長さは別です。要約は最大16,000文字（依存工程ごと最大4,000文字）、全文は保存済みの文脈ファイルで確認します。目安tokensを空欄にしても要約量は変わりません。

自作スキルは `harness-skills/<name>/SKILL.md` を正本とし、`harness-skills/INDEX.txt` に用途・パス・版・status・検証証拠を記録します。experimental / validated / retiredは状態であり、別フォルダへ複製しません。既存台帳があれば再利用し、共有索引は主担当が更新します。採用試験と独立検証はエージェントの作業ルールであり、ハーネスが自動認定するものではありません。全タスク共通への昇格には承認が必要です。

### モデル能力を考慮した計画・割り当て

初回はAPIキーを入力して「保存して取得」を押します。「能力情報を自動割り当てに使う」をOFFのままでも、比較用データだけ取得できます。取得後は検索できる比較表と、各サービスとの照合結果を表示します。外部のキー取得ページは既定ブラウザで開きます。評価されたモデルの名前を、そのままCLIのモデルIDへ入力しないでください。保存中の追加入力は保持しますが、APIキーの未保存入力はディスクへ下書き保存しません。再起動前に保存または取り消してください。

一時的な通信失敗は手動で再取得できます。レート制限（429）の待機時刻は画面に表示し、再起動後も維持します。復号できない保存済みキーには再登録を案内します。キー削除は確認後に実行し、自動更新・割り当てへの反映を停止します（比較用キャッシュは保持）。

「Resources → 利用するサービス → モデル能力 · ベンチマーク」でArtificial AnalysisのAPIキーを登録し、能力情報の利用を有効にします。公式の無料API `/api/v2/language/models/free` から総合・コーディング・エージェント指標と出力速度を取得します。出典・取得日時・指標版を表示し、1日ごとに更新します。キーはElectron safeStorage（Macのキーチェーン）で暗号化保存し、タスク・ログ・エージェントの指示には含めません。取得先にはAPIキーだけを送り、コードや作業内容は送りません。

能力表示はモデル選択欄と設定のモデル一覧にあります。CLIと評価側の区切り文字・Claudeの版番号の位置・Ollamaの`:cloud`を正規化します。同じモデルに推論設定などが異なる評価がある場合は、条件別の範囲を「参考」として表示し、割り当てには指標ごとの測定値の中央値を半分の重みで使います。Claudeの`fable`・`opus`・`sonnet`・`haiku`は、取得データ内でそのシリーズの最新掲載版を参考にします。実際のCLIの版・評価条件は未確認なので、点数の重みは4分の1です。別の版・小型版への曖昧な文字列一致は行いません。空欄のCLI既定、`best`、`opusplan`などはモデルを特定できないため未照合です。参照した評価ID・条件の不確かさは表示とプランナーで共有します。未測定値は補完もゼロ扱いもしません。取得失敗時は保存済みデータを保持し、7日を超えるデータを割り当てには使いません。キー未登録・障害でもタスクは止めません。

プランナーは分担の `capability` に `reasoning` / `coding` / `agentic` / `speed` を指定でき、工程画面に重視する能力と実際の割当理由を表示します。既存計画では任意項目なので移行は不要です。ハーネスは同じ指標版の照合済み候補間だけで小さな加減点を行い、固定担当・権限・利用CLI・使用枠・独立レビュー・継続性の制約を維持します。利用者が選んだモデルを無断で変更しません。外部スコアはHPC/Fortran/MPIや日本語執筆・レビュー精度の保証ではなく、API速度・価格をCLI実測やサブスク残量とは扱いません。

### スキル管理画面

「システム設定 → スキル管理 → スキル一覧・編集」で、共通または保存済みタスクの作業場所を選びます。一覧・本文と適用条件・状態・検証証拠・過去版・取得履歴を確認・編集できます。過去版を編集欄へ戻して保存すると新しい版になり、履歴を上書きしません。保存中の追加入力は保持し、終了時の未保存編集は次回起動時に復元できます。

共通の同梱8スキルは元ファイルを変更せず、アプリ保存領域 `work-skills/<id>/` に編集版を置きます。プロジェクト専用は作業場所の `harness-skills/<id>/SKILL.md` を直接扱います。既存ファイルは試験中として一覧に取り込まれます。GUIでの採用状態・証拠は同じ場所の `harness-state.json`、過去版は `.harness-versions/` に保存します。既存の `INDEX.txt` は参考台帳として保持し、GUIでは上書き・自動同期しません。

新規登録・本文変更は「試験中」、証拠を記入して保存済み本文を「採用済み」にすると次に起動する工程のカタログへ配布します。「廃止」は配布対象外です。採用済みも適用条件・担当に応じて必要時に読みます。追加スキルの採用は保存先ごとに6件までです。実行済み・実行中の保存版は変えません。プロジェクト編集時は同じ作業場所のタスク・CLIを停止してください。エージェントが外部で本文を変更すると採用状態は試験中へ戻ります。

「共通へ登録…」は確認後に指示本文だけをコピーし、共通環境で再試験するため試験中にします。同じIDは上書きせず、元ファイルと補助スクリプトは保持します。スクリプト・参照資料・CLIのグローバル設定は自動コピーしないので、共通化する本文は持ち運べる手順にしてください。SSH先は接続済み環境でのみ管理できます。更新前から維持された接続は再接続してください。遠隔タスクのローカルレポーターには遠隔専用スキルを配布しません。

モード・執筆ルールはそれぞれの設定項目を使い、重複保存しません。実装側の必須ガイダンス（script-reuse / document-checks / related-research）はこの管理画面で無効化しません。

## 基本操作

### GLM Coding Plan（Z.AI / OpenCode）

「Resources → 利用するサービス」で設定します。

1. OpenCodeをインストールし、CLI検出を更新します。動作確認版は1.18.31です。
2. 「接続先」でZ.AIを選び、「OpenCodeログイン管理 → CLIを開く」で、Z.AI Coding PlanのAPIキーをOpenCode公式画面へ入力します。ハーネスはキーを設定・端末ログへ保存しません。OpenCodeの認証保存領域で管理されます。
3. 「モデル一覧を取得」で利用可能なモデルを確認し、`zai-coding-plan/glm-…` のモデルを選んで「OpenCodeに適用」を押します。登録直後など一覧取得に失敗した場合は、CLIの `/models` にあるモデルIDを直接入力できます。
4. タスクの利用CLIにOpenCodeを含めます。Z.AIを独立したサービスとして動的割当・クロスレビュー・レート制限後の引継ぎに利用します。既存タスクのCLI選択は自動変更しません。

このプロファイルはモデルと補助モデルをCoding Planプロバイダーに限定し、専用エンドポイント `https://api.z.ai/api/coding/paas/v4` を指定します。通常の `zai/` や従量課金APIへの自動切替はしません。別プロバイダーのモデル上書きはエラーとして止めます。設定はハーネス起動プロセス内だけで適用し、OpenCodeのグローバル設定を書き換えません。接続先の変更・認証更新は実行停止後に行ってください。

OpenCodeは通常の対話TUIで動き、MCPによる指示取得・管理用結果提出と、実行専用プラグインの最終応答通知を使います。工程完了後も端末は操作可能です。`--auto` により通常操作は自動承認し、ハーネス専用エージェントは追加のCLI内分担・質問ツールを拒否します。読み取り工程では編集ツールを拒否しますが、シェルをOSサンドボックスで制限する仕組みではありません。専用の作業環境を推奨します。

契約残量・リセット日時は現在未取得です。認証情報の「登録済み」は有効な契約・十分な残量の保証ではありません。CLIが返したレート制限は既存のクールダウン・再割当に渡します。タスクの推定トークン予算と契約枠は区別し、未取得の契約枠を0%や架空の残量で表示しません。

遠隔実行では最終SSHマシンにも対応版OpenCodeとZ.AI Coding Planの認証が必要です。ローカルのキーを遠隔へ自動転送しません。

接続方法の出典：[Z.AI公式OpenCode手順](https://docs.z.ai/devpack/tool/opencode)、[OpenCodeプロバイダー設定](https://opencode.ai/docs/providers/)。実モデルへの課金リクエストなしでの連携検証は `ELECTRON_RUN_AS_NODE=1 node_modules/.bin/electron scripts/smoke-opencode.cjs`（ローカル模擬モデル＋実OpenCode TUI）、設定画面の検証は `npm run test:layout -- --glm-only` で実行できます。

### Ollama Cloud Pro（OpenCode）

同じ「Resources → 利用するサービス」で、接続先を「Ollama Cloud（APIキーで直接接続）」に切り替えます。

1. Pro契約のOllamaアカウントで [APIキー](https://ollama.com/settings/keys) を発行します。Proの契約・購入をアプリから行うものではありません。
2. 「OpenCodeログイン管理 → CLIを開く」で、そのAPIキーをOpenCode公式画面に入力します。認証先は `ollama-cloud` に固定され、ローカルOllamaやZ.AIの認証とは区別されます。
3. 「モデル一覧を取得」から `ollama-cloud/…` のモデルを選び、「OpenCodeに適用」を押します。モデル一覧はCLIのカタログであり、現在の契約での利用可否を保証するものではありません。キー未登録・取得失敗時はCLIの `/models` にあるモデルIDを直接入力できます。
4. タスクで利用するCLIにOpenCodeを含めます。既存の担当指定・モデル上書きは変更しないため、Z.AI用のモデルが固定されている場合はOllama用に変更するか上書きを外してください。

OpenCodeから `https://ollama.com/v1` に直接接続します。Ollamaサーバーのローカル起動・モデルダウンロードは不要です。通常モデルと補助モデルの両方をOllama Cloudに固定し、別プロバイダーへ暗黙に切り替えません。APIキーはOpenCodeで管理し、ハーネスの保存設定や起動引数に含めません。リモート実行も同じ接続方式ですが、最終マシン側でOpenCodeの認証が必要です。

OpenCodeで使う接続先は一度に1サービスです。Z.AI／Ollamaそれぞれの前回モデルとOpenCodeの認証登録は保持されます。切替はタスクとOpenCode端末の停止後に限り、過去の実行は元のサービスの使用履歴として残します。Z.AIとOllamaを同時に別担当として割り当てる機能ではありません。

契約の使用率・残量は、下記の「残量表示を連携（任意）」でWeb画面と連携できます。モデル実行のための再ログインではありません。CLI認証情報の「登録済み」からPro契約の有効性は判定しません。[Ollamaの使用状況](https://ollama.com/settings)で追加課金設定も確認してください。ハーネスは購入・チャージを実行しませんが、契約内使用量だけでの停止や追加クレジット不使用を保証するものではありません。契約側の設定を確認し、必要に応じてハーネスの推定トークン予算も設定してください。

出典：[Ollama Cloud公式仕様](https://docs.ollama.com/cloud)、[OpenCodeのOllama Cloudプロバイダー定義](https://github.com/anomalyco/models.dev/blob/dev/providers/ollama-cloud/provider.toml)、[Ollamaのプラン・利用枠](https://ollama.com/pricing)。料金・枠の数値は固定せず、サービス側の現行設定を参照します。

検証：`ELECTRON_RUN_AS_NODE=1 node_modules/.bin/electron scripts/smoke-opencode.cjs --ollama` は実OpenCodeの対話TUIでローカル模擬応答を使い、指示取得・結果提出・完了通知を確認します（実APIへの推論リクエストなし）。GUIは `npm run test:layout -- --ollama-only` で確認できます。契約したモデルへの実接続はAPIキー登録後に確認が必要です。

### インストール済みOllama経由のDeepSeek V4.1 Flash

すでにOllama経由のOpenCodeで使えている場合、APIキーを再登録せず、そのOllamaのログインを利用できます。

1. Ollamaを起動したままにします。
2. 「Resources → 利用するサービス」で「DeepSeek V4.1 Flashを選択（Ollama経由）」を押します。
3. モデルが `ollama/deepseek-v4.1-flash:cloud` になったことを確認し、「OpenCodeに適用」を押します。
4. タスクの利用CLIにOpenCodeを含めます。既存タスクで旧モデルを固定している場合は、その上書きを外すか変更してください。

この方式は実行マシンの `http://127.0.0.1:11434/v1` に接続します。Cloudモデルなのでローカルへの重みダウンロードは行いません。モデル一覧はOllamaのOpenCode連携設定、OpenCodeの最近使ったモデル、ローカルOllamaのモデル一覧からCloudモデル名のみ取得します。`ollama list` が空でも、保存済みCloudモデルを選べます。任意ポート・非標準の設定保存先は現在未対応です。

設定はOpenCode起動時のみ渡し、既存のOpenCode設定ファイルやOllamaの認証を書き換えません。DeepSeekの入力文脈は1M、出力はハーネス側で保守的に16,384 tokensに設定します（契約上限ではありません）。通常モデル・補助モデルを同じ接続先に固定し、ハーネスのMCP指示取得・結果提出・対話端末を維持します。SSH実行では最終マシン側にも起動済みOllamaとログインが必要です。MacのOllamaへ自動転送はしません。

直接API方式とOllama経由方式は同じCloudサービスとして使用量履歴を扱い、別の利用枠が増えたようには表示しません。契約残量のWeb連携は任意です。未連携や取得失敗をCLIの認証失敗とは扱わず、既存のOllamaログインで作業できます。OpenCodeログイン管理の接続確認はローカルOllamaの稼働確認のみで、CloudログインやPro契約の有効性の保証ではありません。

出典：[Ollama公式OpenCode連携](https://docs.ollama.com/integrations/opencode)、[DeepSeek V4.1 Flash公式モデル](https://ollama.com/library/deepseek-v4.1-flash)。

検証：`ELECTRON_RUN_AS_NODE=1 node_modules/.bin/electron scripts/smoke-opencode.cjs --ollama-app` は模擬モデルで実OpenCodeのMCPと完了通知を確認します。`--live` を加えた場合だけ実Cloudモデルを呼び出し利用枠を消費します（ユーザーの作業とは隔離し、テスト用MCP以外のツールを禁止）。GUIは `npm run test:layout -- --ollama-app-only` で検証できます。

### Ollama CloudのUsage表示（Web連携）

1. 残量表示が必要な場合だけ「Resources → 利用するサービス → 残量表示を連携（任意）」を開きます。右サイドバーのOllamaをクリックした詳細画面からも開けます。CLIの利用だけなら、この操作は不要です。
2. 「ログイン・Usage画面を開く」を押し、専用ウインドウで公式サイトにログインします。**Ollama／OpenCodeと同じアカウント**を使ってください。アカウント一致は自動検証しません。
3. 公式SettingsのUsageが表示されたら、ハーネスの「Usageを取得」を押します。以後は約5分間隔で自動確認します。手動再取得は30秒以上間隔を空け、失敗時は間隔を延長します。

公開Quota APIではなく、ログイン済みの `https://ollama.com/settings` の使用量カードを読み取ります。旧プランのSession／Weekly、新プランのMonthly／Included usage、表示される追加クレジット残高に対応します。取得できない枠や上限は推測しません。明示されたタイムゾーン付きリセット日時はMacの日時表示へ変換し、相対時間しかない場合はその表記を取得時点の情報として保持します。画面変更・未ログイン・通信失敗時は前回値と取得失敗を区別し、0%として上書きしません。プラン変更後の成功した全体スナップショットで、旧プランの枠を置き換えます。

ログインはアプリ専用の永続ブラウザ領域に保存し、通常ブラウザのCookieやCLIの鍵を読み取りません。Web画面にはNode.jsやハーネスの操作APIを公開せず、認証・公式サイト以外への移動を制限します。パスワード等のフォーム内容や画面全体を記録せず、Usageの数値・リセット情報だけ保存します。購入・チャージ・契約変更は自動では行いません。「Web連携を解除」は専用領域のログインを消去し、CLI側の認証は変更しません。メールログインを基本とし、Google/GitHub側で埋め込みブラウザが拒否される場合はメールログインを使ってください。

CLI側の状態と残量取得の状態は別表示です。Ollama経由では「Ollama接続済み」と「残量：未確認」を同時に表示でき、モデル選択だけでWeb連携を開始しません。CodexはCLIのapp-server、Claude CodeはCLIのOAuth認証情報で使用量APIを読みますが、残量取得の401/403はCLI本体のログアウトを意味しません。CLIで作業できている場合は再ログイン不要です。取得失敗時に残量を0%として扱うことはなく、確認済みの使用制限や実際のCLI認証エラーは引き続き保持します。

テスト：`node_modules/.bin/electron scripts/smoke-ollama-usage.cjs` は一時的なブラウザ領域と模擬公式ページだけを使い、旧／新プラン・日付・失敗・分離を検証します。`npm run test:layout -- --ollama-usage-only` はログイン導線とサイドバー表示を検証します。実アカウントでの初回確認にはユーザーのWebログインが必要です。

### 遠隔CLIでの開発（SSH初期版）

ハーネスはMac、CLI本体とそのファイル操作・シェルは遠隔ログインノードで動作します。スケジューラ専用アダプターは不要です。各施設の利用手順をプレーンテキストで登録し、CLIがそれに従ってバッチスクリプトを作成・投入・監視します。ジョブIDの記録と既存ジョブの確認を指示しますが、スケジューラ側の厳密な一度だけの投入を保証するものではありません。

#### 先に接続を準備してから作業を渡す（追加SSH対応）

1. `システム設定 → 遠隔システム（SSH）` で接続方式を `手動で接続を準備（追加SSHに対応）` にし、最初に接続するマシンのIP・ユーザ名を保存します。既存の登録先は従来方式のままなので、切り替える場合は明示的に変更・保存してください。
2. `Resources → 作業環境 → 接続・CLI端末 → SSH接続` を押し、アプリ内の端末でログイン・追加のSSH・多要素認証を行います。最終マシンで必要な `module load` や環境変数の設定を行い、`mkdir -p`・`cd` で作業フォルダへ移動します。この方式では登録欄の作業フォルダ・起動時設定を自動適用せず、ユーザが準備した現在のフォルダと公開済み環境変数を使います。
3. 最終マシンのシェルのプロンプトが出た状態で `ここを作業環境として確定` を押します。パスワード入力中には押さないでください。確定したホスト名・ユーザ名・絶対パス・利用可能なCLIを表示します。以後この接続端末は連携専用となり、CLIはタスクの実行画面の別端末で表示・操作できます。
4. `この接続先でタスクを作成` で新規作成するか、`既存の未開始タスクへ渡す` で対象を選び `確定した環境をこのタスクに割り当て` を押します。既存のゴールは保持します。本作業を始めたタスクの移動やプロジェクトファイルのコピーは行いません。ゴール整理の端末が残っている場合は、先に閉じてください。

最終マシンに **Node.js 18以上・Python 3.6以上（標準ライブラリのPTY対応）・使用するCLIと認証** が必要です。POSIX環境を対象とし、確定時のシェルはsh/bash/zsh形式を前提とします。他のシェルの場合は最終マシンで `bash` を起動してから準備してください。中継マシンにNode・Python・CLIは不要です。詳細設定のNode/Pythonは最終マシンの実行ファイル名またはパスです。シェルの未公開変数・関数・エイリアスはCLIに継承されません。

すでに通した多段SSHの同じ接続上で、CLIの本物のPTY・ファイル操作・完了通知・報告書取得を多重化します。最初のマシンへ別途接続し直しません。連携プログラムはメモリ上で起動し、パッケージのインストール、TCP待受け、SSH鍵の転送、常駐サービス登録はしません。Terminal.app等で開いた外部の既存セッションの取り込みには対応せず、アプリの接続用端末で準備する必要があります。

アプリ終了・接続断で連携は終了し、自動再ログインしません。再開時はユーザが再接続し、保存された最終ホスト・ユーザ・ホーム・作業フォルダ・Node実行パスが一致することを確認します。投入済みバッチジョブは自動取消ししません。再開前にジョブ・CLIの残存状態を確認してください。以下の管理ファイル・報告書・施設の利用許可に関する注意事項は、この方式にも適用されます。

#### 実行が途中で止まる場合（両方の接続方式）

遠隔Codexの起動権限は、`システム設定 → 遠隔システム → 遠隔Codexの起動権限` で選択できます。新規接続先の標準は **Full access**（bwrapなし）で、工程別サンドボックスは明示選択した場合に使います。既存接続先は設定を保持し、古い設定の未指定値も従来のサンドボックスとして扱います。Full accessはリスク確認後に保存でき、この接続先で今後作るタスクの各Codex起動に `--sandbox danger-full-access --ask-for-approval never` を指定します。対話画面で工程ごとに切り替える必要はありません。これは隔離環境を修理する設定ではなく、Codexのサンドボックスと承認要求を使わない設定です。ログインユーザがアクセス可能な作業フォルダ外のファイルやネットワークにも操作が及ぶ可能性があります。計画・調査・レビューも書込禁止がOSで強制されず、役割の指示だけになります。施設・組織のポリシーやOS権限は変更せず、ローカルCodex・他のCLIの起動設定は変えません。[公式の権限設定](https://developers.openai.com/ja-JP/docs/agent-approvals-security)

既存タスクには設定を自動反映しません。停止した遠隔タスクの `遠隔Codexの権限… → Full access → 権限をこのタスクに保存` で、ゴール承認前でも個別に適用できます。承認済みタスクでは従来の「実行環境を復旧…」からも変更できます。残存するエージェント端末は事前に終了してください（SSH接続は保持できます）。保存だけでは接続・診断・作業開始を行いません。ゴール・計画・履歴・成果物は保持し、権限の異なる以前のCLI会話は分岐せず、引き継ぎ情報から新規会話で実行します。起動時の権限は実行履歴にも保存します。

Full accessを保存したタスクの診断では、通常コマンドとCLIのバージョン起動だけを確認します。サンドボックス未使用・未検証であることを表示し、`unshare` や `bwrap` の成功を再開条件にしません。これを隔離環境の復旧成功や、Codexの全機能・書込権限・利用許可の検証として扱わないでください。サンドボックス設定のタスクでは従来どおり隔離環境のチェックが必要です。

停止した遠隔タスクの右上にある **「実行環境を復旧…」** から、同じタスクを引き継いで復旧できます。

1. **接続・診断**：切断されていれば認証画面を開きます。多段SSHでは以前と同じ最終マシン・ユーザ・作業フォルダへ接続してください。診断だけではタスクを開始・リセットしません。
2. 診断結果に従って、接続先のターミナルや施設管理者を通じて必要な環境修正を行い、再診断します。CLI未検出・バージョン実行失敗、またはサンドボックス設定でのCodexのLinuxサンドボックス失敗が残る間は再開できません。障害を理由に権限を自動拡大する処理や、自動インストールは行いません。既存接続を作り直す場合は、残っているエージェント端末を閉じてシステム設定から切断してください。
3. **復旧を確認して再開**：再度診断に合格した場合だけ未完了工程から続行します。ゴール・完了済み計画・成果物・過去ログは保持し、失敗工程に依存するレポート・レビューは再検証します。`completed` の応答でも、環境障害で実作業ができなかったことが明示されたワーカーは再実行します。通常のユーザ判断待ちや未送信の追加指示を飛ばす操作ではありません。

再開担当には、既存バッチジョブのID・稼働状態・部分成果を確認し、状態不明のまま重複投入や取消しをしないよう指示します。スケジューラ専用管理やジョブ状態の自動保証は行いません。環境修正は手動、接続確認・再診断・同じ工程からの再実行をハーネスが担当する機能です。

停止の診断：`bwrap: setting up uid map: Permission denied` 等で作業が進まないときは、作業環境を確定した状態で `Resources → Codex → 接続・CLI端末 → 接続・CLIを診断` を押してください。同じ接続の最終マシン上で、通常コマンド、Codexバージョン、Linuxのユーザ名前空間・AppArmor関連の読み取り可能な情報、Codexの読取用／作業用サンドボックス内での無操作コマンドを確認します。LLM呼び出し・OS設定変更・インストール・再ログイン・ジョブ投入はしません。各診断コマンドは8秒で打ち切りますが、タスクのCLIを時間制限で終了させるものではありません。Mac上の接続ではLinux固有テストは省略します。診断成功はCLIの全機能・書込み境界・施設の利用許可を保証するものではありません。

通常コマンドだけ動いて隔離環境が失敗する場合は、診断結果を施設管理者に提示して、対応するbubblewrapとユーザ名前空間の許可・AppArmorプロファイル等を確認してください。保護を自動解除する処理はありません。参照：[公式のLinuxサンドボックス前提条件](https://learn.chatgpt.com/docs/sandboxing)。ワーカーの応答受領と作業成功は区別して表示し、`ask-user` は「要対応・作業未完了」、`needs-work` は「残作業あり」と表示します。停止理由はタスク内の全タブに表示します。具体的なサンドボックス初期化拒否を報告した `needs-work` はユーザ確認へ切り替え、同じ失敗でモデルの再試行を繰り返しません。環境障害は上記の復旧画面から再開し、作業方針に関する確認は追加指示で回答してください。

#### 接続先で直接CLIを起動する（従来方式）

1. `システム設定 → 遠隔システム（SSH）` で表示名と接続先を入力します。接続先にはIPアドレス（例：`192.0.2.10`）やサーバ名を直接指定でき、SSH configへの登録は不要です。ログインユーザ名を別欄に入力し、ポートは通常空欄（標準22、既存SSH設定があればそちら）にします。Macの `~/.ssh/config` に登録済みのHost名も使えます。踏み台や鍵は既存SSH設定で指定します。管理用IDは自動作成するので通常は入力不要です。
2. 遠隔Node.js 18以上、bash、使うCLIとその認証、TeX・作図環境をあらかじめ準備してください。必要なら「起動時の環境設定」に `module load ...` などを記入します。この欄だけは、接続時に実行するシェル命令です。「利用手順」はエージェントが読む文章です。CLIの環境互換性・サンドボックス対応・外部LLM通信・ログインノード上での継続実行・情報持ち出しについて施設の許可が必要です。アプリはソフトのインストールや認証の緩和を自動実行しません。
3. 作業フォルダには `projects/test` または `~/projects/test` のようにログイン先のホームを基準に入力します。空欄は `~/agent-harness` です。`Resources → 作業環境 → 接続・CLI端末 → SSH接続` でホスト鍵・パスワード・MFA等を確認したあと、`ここを作業環境として確定` を押すと不足するフォルダを作成し、実際の絶対パスと利用可能なCLIを表示します。既存ファイルは上書きせず、`..` やホーム外へ出るリンクは拒否します。共有領域などは `/work/project` のような絶対パスでも指定できます。Node.jsのコマンドは「計算ノード名」ではなく連携プログラム用の実行ファイル名です。詳細設定の `node` は通常変更不要です。CLI自体のサインインや初回フォルダ信頼確認は、初回のタスク端末でも必要になる場合があります。
4. Dispatchの `実行環境` で登録先を選びます。事前のSSH接続・環境確認は任意です。未接続なら「AIでゴール整理」やタスクの実行・再開・キュー開始時にSSH認証ポップアップが開きます。端末でパスワード・MFA・ホスト鍵を確認し、`環境確認して続行` を押すと不足フォルダを作成してCLIを起動します。認証前にはCLIを起動せず、取り消してもタスクは保持します。認証待ちを取り消しても別のタスクは停止しません。複数タスクの認証画面は一つずつ表示します。同じ登録接続先の同時実行は共有フォルダの競合を避けるため拒否します。認証済み接続は再利用し、パスワードは設定に保存しません。タスクは接続先と利用手順のスナップショットを保持します。ゴール設計・作業・レポート・独立レビューをすべてその遠隔環境で行います。遠隔端末は標準で色付きの `CLI原画面・操作` を表示します。
5. 遠隔の作業フォルダ内 `.agent-harness/<task-id>/` に当該タスクの補助スクリプト・管理データ・報告書を保存します。初期テンプレートは一度だけ転送し、遠隔で編集されたファイルをローカルの古い版で上書きしません。工程完了時にTeX/PDF/図表をMacのタスク報告書フォルダへ取得し、既存のPDFプレビューを利用します。プロジェクト全体は同期しません。遠隔管理フォルダはバージョン管理に含めないでください。

接続先の一覧はアプリデータの `remote-systems/systems.json`、利用手順は同フォルダの `<id>.txt` です。手順にはジョブ投入・状態確認・取消の例、キュー・課金アカウント、計算資源の上限、出力先、ログインノードの禁止事項を記載してください。認証情報は書かないでください。通常の手順編集は新規タスクに反映され、既存タスクの承認済み手順は変更しません。

保存後の `この接続先でタスクを作成` は、その接続先を選択したDispatchを開きます。未保存の変更がある場合は保存を促し、古い設定で作成しません。設定画面を開き直したときは、前回選択した保存済み接続先を表示します。既存タスクの作業場所は自動変更しません。

従来方式の接続は認証済みのSSH masterを共有します。ファイル・完了通知は1本の長寿命の補助チャネルで扱い、CLIの対話画面は別のPTYチャネルを使います。masterが失われたときに、補助操作が新規ログインへ勝手に切り替わることはありません。接続先に応じた同時チャネル制限は適用されます。

遠隔端末はtmuxが利用可能なら保持します。SSHを再接続し「中断した工程から再開」で元のCLIへ戻ります（接続認証の自動再試行はしません）。tmuxがない環境の自動設定は従来の直接端末を使い、終了確認後に未完了工程を再試行します。残存CLIや状態不明のロックがあれば二重起動を止めます。ロックは時間だけでは解除しません。Mac終了や一時停止で投入済みのバッチジョブは自動取消しません。再開前にCLI・ジョブの残存状態を確認してください。遠隔の完全な白紙やり直しは、別の空の作業フォルダを登録して新規タスクを作成します（既存コードは削除しません）。

遠隔の認証はMacと同一アカウントと仮定せず、使用枠を別表示にします。Claudeが遠隔のstatus hookで報告した枠は取得し、未報告の枠は不明のままです。遠隔CodexのCapacity自動プローブは未対応です。使用枠・トークン数を推測で実測値として表示しません。報告書の転送は250MB・5000ファイル、1ファイル100MBまでで、リンクや特殊ファイルは拒否します。レビューの根拠は遠隔の実ファイルを範囲確認してハッシュ検証します。

ローカルの疑似SSHトランスポートとGUIテストで検証しています。施設固有のSSH認証・CLI互換性・実スケジューラへの投入は、利用する接続先で小さなテストジョブを用いて別途確認してください。

### ローカルと共通の操作

タスク一覧は左サイドバー、契約先ごとの使用量・リセット時刻は右サイドバーに常時表示します。左右の境界はドラッグで幅を調整できます。左のタスクを選ぶと、設定やDispatch画面からもそのタスクに戻ります。Executionの「工程・担当」は標準で開き、担当名・工程名・状態を簡潔に表示します。折りたたみと高さ調整も可能です。

Executionの端末は、ローカル・遠隔とも色付きのCLI原画面だけを表示し、クリックしてキー入力できます。画面モニター・画面履歴・表示クリアは廃止しました。原画面の出力は改変しないため、CLI自身が描画したJSONもそのまま表示します。通常の外部ログとワークフローの管理データは保持し、作業履歴の管理用JSONの文章化は完了判定には使用しません。

1. 左サイドバーの `Dispatch` を開き、最初に作業場所を確定します。ローカルは新規作成／既存ディレクトリを選び、絶対パスを入力するかダイアログで選択します。新規フォルダはタスク作成時に作成し、既存ファイルを上書きしません。遠隔は登録先の作業フォルダを確認します。その後に目的、運用方針、使用可能なCLIを指定します。`AIでゴール案を作成` または `自分でゴールを設定` を押すとTasks画面へ移ります。
2. 新規タスクの `Goal` で目的を入力し、成果物・達成条件をチェックして選択します。足りない項目は「＋ 追加」、検証方法や本文は各行の「検証方法・編集」から入力します。制約・対象外・進め方は折りたたみ内です。未解決の確認事項は回答をゴールへ反映してから「反映済み」をチェックします。`ゴールを承認してキューへ` で初めて本作業を実行可能にし、`Run workflow` または `Run queued tasks` で開始します。
3. オーケストレーターがPlan、Execute、Reviewの担当CLIを工程ごとに決定します。
4. レート制限時は同じ工程を別の利用可能な契約先へ自動的に引き継ぎます。
5. 最後にReportエージェントがレポート用CLIとしてTeXをビルドします。失敗した場合はログを調べて`report.tex`等を修正し、PDFができるまで再実行します。
6. `Resources` で利用状況と割当ポリシーを確認します。TeXメモとPDFは各タスクの詳細画面に表示されます。
7. TeX・作図ツールのコマンド、引数、レポート保存先は、左サイドバーの `システム設定` で設定・検査します。

### ゴール設定支援（自律ハーネスの第1段階）

ゴール設定はチェックリスト形式です。チェックは「作業に含める」であり、達成済みの判定ではありません。条件の「必須／追加改善」は別に指定します。未選択の項目も候補として保存され、保存・再起動後に選び直せます（`goal.unselected`）。候補は承認条件・本作業プロンプト・実行用コンテキストの対象から除外します。各リストは選択中＋未選択で最大40件です。AIによる再提案でも候補を保持し、承認前の確認は省略しません。追加欄の入力途中の文字も画面更新で保持し、「＋ 追加」前に承認して取りこぼすことを防ぎます。

詳細の開閉はタスク・ゴールの版ごとに保持します。「確認事項」の各項目の直下に回答欄があります。記入後に「回答を使ってAIでゴールを更新」を押すと、質問と回答を対にしてAIへ渡し、目的・条件などへ反映した下書きを再提案します。「下書きを保存」でも回答を保持でき、AI更新の失敗時にも消えません。反映済みの回答はゴールの変更履歴で確認できます。手動の「反映済み」はユーザが回答をゴールへ反映したことの確認であり、回答欄に入力しただけでは承認できません。必須条件・成果物の不足、選択中の条件の検証方法不足、未解決の質問、古い版からの上書きは引き続き拒否します。本作業開始後の条件変更は許可しません。

AIによる整理は、選択したCLIを通常の対話ターミナル上で読取専用の1工程として実行します。本作業やTeXビルドは行わず、ゴール案と不足情報の質問を返します。CLIの利用枠を消費します。ほかのタスクの実行中でも異なる作業フォルダなら整理を開始できます。同じフォルダ（リンクの別名を含む）や親子フォルダでの同時実行は拒否します。`Execution`で動作を確認でき、整理完了時は`Goal`に戻ります。

手動編集後の`下書きを保存`、回答を加えた`編集内容・回答からAIで再提案`、ユーザによる承認に対応します。成果物・必須条件・各条件の検証方法が不足している場合や、確認事項が残っている場合は承認できません。AIの出力が不正なら元の下書きを保持し、手動編集・再提案で復旧できます。一時停止・再開でも承認を飛ばしません。

承認済みでも本作業を開始する前なら `編集内容・回答からAIで再提案` を利用できます。再提案時に下書きへ戻し、改めて承認するまで本作業は実行しません。過去の承認内容はゴール履歴に残します。

ゴールは版番号と変更履歴を保存し、古い画面からの上書きを拒否します。承認した条件を全工程のプロンプトへ渡します。編集して再保存すると承認は解除されます。本作業開始後のゴール変更・影響範囲に基づく再検証は後続段階です。主担当方式は下記の会話引継ぎ・分担・予算目安による着手制御に対応します。承認は要件の確定であり、条件を達成したという判定ではありません。運用情報はTeX本文ではなくアプリ内部と外部ログに保存します。

### 作業モード・プリセット

Dispatch の「作業モード」の初期選択は研究モードです。アイディア／関連研究調査／コーディング（実装）／大規模コード移行・GPU化／論文執筆／ポスター作成も選べます。「指定なし」は従来の標準ルールです。再読み込みで選択を戻しません。ゴール案には用途に応じた成果物・達成条件・確認事項を入れますが、承認前に編集できます。選択だけでは本作業を開始せず、権限・トークン予算・モデル・同時実行数を変更しません。

大規模コード移行・GPU化モードは、基準実行→CPU再現テスト→小単位の移行→数値・統合・MPI検証→性能評価を進めます。タスク内の「移行・検証・ジョブ」で単位別の数値比較、変更後の合格無効化、ジョブ状態と資源予算を管理します。主担当はHPC管理操作で単位を登録し、未検証のまま最終レポートへ進めません。独立実装はGit worktreeに分離し、担当ファイル・基準ハッシュ・単体検証を確認してから共有作業場所へ統合します。研究モードの構成は変更せず、出力は技術レポートTeX/PDFです。[利用方法と制限](hpc-refactoring.md)を参照してください。

研究モードは「アイディア→関連研究調査→コーディング（実装）→論文執筆」の4モードを順に実行します。タスク作成時に各モードのユーザー編集済みルールと版番号をまとめて保存し、各工程の計画・実作業・検証・TeX執筆へ対応するモードのルールを渡します。ゴールのAI設定にも各モードのゴール設計ルールと初期候補を渡します。工程ごとに主担当が計画と必要な専門担当を設計し、既存成果・TeXメモから引き継ぎます。別モードへ移るときはCLIの会話を新しくし、前モードの作業制約を引きずりません。計画は読み取り専用、実作業は各モードの範囲内でTeX等を更新します。単独モードの「次工程へ進まない」は担当自身の境界であり、アプリは承認された研究全体の次工程へ自動で引き継ぎます。最後に論文・標準技術レポートのPDFを生成し、全工程の検証ルールで異なるCLIによる2回の独立レビューを行います。

システム設定で各専用モードを編集すると、それ以降に作る研究タスクにも反映されます。「研究モード」の編集欄は研究全体の統合方針です。構成モードのルールが読み込めない場合、別のルールで代用せず研究モードを利用不可にします。既存タスクは保存済みのルールと工程を保持し、新しい4工程方式へ自動移行しません。新方式の追加作業・レビュー差戻しでは4工程を順に確認しますが、完了済み成果を再利用し、指摘に関係する部分だけを修正します。元のゴール・予算・権限は変更しません。

関連研究調査は文献比較に、実装は選んだ方針の本格実装・デバッグ・テストに、論文執筆は提供済み成果の文章・図表・引用の仕上げに専念します。新しいアイディアモードは書き込み禁止ではありません。同じ課題に対して複数の方法や組合せを探索し、小規模な試作実装・実機での予備評価・反証実験を行って有望な候補を絞ります。ベースラインと比較し、候補ごとのコード・条件・実測値・採用／棄却理由を保持します。主担当は承認済みの作業場所へ書き込めますが、計画・専門担当・独立レビューは引き続き読み取り専用です。別環境や承認範囲外の大規模実験へ勝手に拡張しません。アイディア・関連研究調査・実装は技術レポートTeX/PDF、研究・論文執筆は論文TeX/PDFも作ります。

システム設定は「実行の基本設定」「作業・執筆ルール」「スキル管理」「作業環境」の4入口です。CLIや契約の設定はResourcesに集約しています。作業・執筆ルールは共通原則／モード別／執筆ルールを切り替えて編集します。モードは6項目で編集し、全文は参照用です。既存ルールの形式を読み取れない場合だけ全文修復を許可します。ゴールのチェックリスト候補は詳細設定です。ユーザーの編集済みルール・初期候補・既存タスクの承認範囲は変更しません。

旧調査モードのID `research` は関連研究調査用として維持し、新しい統合研究モードは `research-project`、アイディアモードは `idea` です。既存タスクの保存済みルール・モードは移行しません。ユーザー編集済みの作業ルールとゴール初期候補も上書きせず、選んだモードの範囲と矛盾する場合は確認するよう指示します。

アイディアが固まったら、タスク上部の「担当・確認設定…」で追加指示を「修正・続行」にし、「実装・実験へ進む」にチェックします。実装対象・実験条件・検証方法を追加指示に記入し、「実装・実験のゴールを確認」を押してください。同じタスク・作業フォルダ・成果物を保持したまま、実装モードのルールと新しいゴール下書きへ移ります。以前の「実験しない」などの制約・対象外は勝手に削除しないので、Goal画面で見直して承認してください。承認後にキューから実行すると、主担当の計画→実装・実験→技術レポート→2回のレビューへ進みます。次回用の保存だけでは切り替わらず、移行ボタンでも承認前にCLIは動きません。旧ゴール・旧モード・ログは履歴に保存し、OS権限・SSH接続先・トークン予算は変更しません。

停止したところから承認範囲を直接変えて続ける場合は、モードに関係なく「修正・続行」の追加指示を記入し、「作業範囲・制約を変更して実行…」を使います。確認画面で解除する制約・対象外だけをチェックし、必要なら「実装・精度検証・性能実験を含める」を選んで「変更を承認して実行」を押します。この操作はゴールを新しい版として承認し、そのまま次のラウンドを開始します。追加指示だけでは古い禁止事項は消えません。「着想検討に専念」と「実装・実験は対象外」が両方ある場合は両方を見直してください。FP64禁止など選ばなかった条件と既存の成果物・達成条件は保持します。キャンセルや保存のみでは実行範囲を変更せず、確認後にゴールが更新されていた場合は古い承認を拒否します。OS権限・SSH接続先・予算の変更は行いません。

システム設定の「作業プリセット」で、用途ごとの作業ルールと「ゴールの初期候補を編集」にある成果物・達成条件・検証方法・質問をまとめて編集し、「プリセット全体を保存」で一括保存できます。初期候補は各20件まで、標準IPSJ報告書の成果物・条件はタスク作成時に別途追加します。質問は不要なら空にできます。複製操作はありません。各作業ルールは `## 共通`、`## ゴール設計`、`## 主担当の計画`、`## 作業`、`## 検証`、`## レポート` の6節です。この「共通」はそのモード内の全担当向けで、担当には関連する節だけを渡します。

全モードに適用する基本方針は、独立した「全モード共通の作業原則」で編集・保存します。対象は6プリセットです。「指定なし」の標準モードには後付けしません。執筆時の表現・媒体別のルールは「レポート執筆ルール」で管理します。原則を編集してもアプリ側の必須の権限・承認・予算・レビュー・PDF確認は省略できません。

ユーザ版は `work-presets/<mode>/settings.json` に作業ルールと初期候補を1つのファイルとして原子的に保存します。不正な初期候補や全体100KB超過は保存前に拒否し、片方だけを更新しません。共通原則は `work-presets/common.md` です。従来の `rules.md` は新設定がない場合に読み込み、移行後も削除せず保持します（新設定の保存後はこちらが優先）。他モードへの切り替えや再読み込みでも未保存のプリセット編集を保持し、競合する保存は拒否します。

同梱の初期値は `assets/work-presets/<id>/preset.json` と `rules.md`、共通原則は `assets/work-presets/common.md` です。保存先は画面にも表示します。初期値との二重表示はせず、常に用途ごとの有効な設定1つを表示します。古い版からの保存、見出し欠落・重複、過大なファイル、シンボリックリンクは拒否します。以前に作ったコピーはディスクと既存タスク内に保持しますが、新規タスクの選択肢からは外します。

タスク作成時にルール・共通ルール・ゴール初期値・内容ハッシュをコピーして保存します。プリセットの後日の変更は既存タスク、再開、追加ラウンドには反映しません。Task のGoalに保存済みルールを表示します。Dispatchで選択後にファイルが変更された場合や、古い編集画面から保存した場合は、そのまま上書きせず再確認を求めます。既存タスクにモードを自動付与する移行は行いません。

論文・ポスターの汎用LuaLaTeXひな型を `assets/document-templates/` に同梱しています。公式投稿様式ではなく、初期値は論文A4・ポスターA0縦（841×1189mm）です。希望の寸法・向き・投稿様式はゴールで指定・承認し、エージェントがTeXを調整します。テンプレートはルールの直接編集でも保持します。本文もタスク作成時に固定保存し、既存タスクには後から自動追加しません。

標準IPSJ報告書の横に、`paper/main.tex` または `poster/main.tex` と各 `main.pdf` を作成します。ゴール承認前は成果物を作成せず、作成後のソースは状態更新で上書きしません。作業担当が内容を執筆し、レポーターが全PDFを再ビルド・エラー修復、レビュワーが内容と体裁を確認します。追加PDFが欠落・不正・前回のままなら完了にしません。LuaLaTeXと必要なパッケージは事前に用意してください（各成果物の `.latexmkrc` とローカルフォントキャッシュを使用）。

Task のReport内の「PDF成果物」で標準報告書／論文／ポスターを切り替え、「レポートの版」で過去ラウンドを確認できます。各TeXとPDFを版ごとに保存しますが、外部画像・文献ファイル一式の再現可能なアーカイブまでは行いません。ルール管理のMarkdownと、実作業メモ・報告書のTeXは別用途です。

「実行計画・体制」は1作業単位につき1カードで表示します。同じCLIでも別作業は分け、同じ作業の再試行はカード内の実行履歴にまとめます。実行中のカードは初期状態で展開し、終了・待機は折りたたみます。状態が変わらない間は手動の開閉を保持します。独立した読み取り専用の専門作業は横並びにし、レポーター・各レビューも独立カードとして表示します。受け渡し関係と待機元は作業番号で示し、過去の計画・撤回した作業は末尾の履歴へまとめます。表示の変更だけで、実行順序・割当・完了判定は変更しません。

「作業履歴」は回ごとに、状態別の工程件数・工程一覧・担当と時刻付きの報告カードを表示します。工程一覧は登録順であり、並列工程の実行順や依存関係を表す図ではありません。完了件数はゴール達成率ではありません。各工程を選ぶと報告へ移動でき、本文は個別または一括で開閉できます。状態更新後も開閉とスクロール位置を保持します。保存済み本文の見出し・箇条書き・表・コードをテキストとして整形し、HTML・スクリプト・画像は実行／読み込みません。報告の冒頭は抜粋であり、AIが生成した要約ではありません。元ログ、過去の回と中断前の記録は変更しません。

### レポート執筆ルール（TeX執筆の全経路に適用）

システム設定 →「レポート執筆ルール」は「共通ルール」「表現・文体（AIらしい表現を避ける）」「数値・文献の検証」「論文・レポート」「ポスター」「スライド」の6区分です。各見出しをクリックしてSKILL.md形式の本文を直接編集・保存します。文書ごとに共通＋表現＋検証＋その媒体の1区分を使い、タスク名や作業プリセットだけで媒体を決めません。表現の見直し候補は日本語・英語の指示に統合し、追加分を別の規約として重ねません。

同梱ルールは `assets/finishing-skills/` 以下の `de-ai-style/SKILL.md`（共通）、`report-writing-style/SKILL.md`（表現）、`report-writing-verification/SKILL.md`（検証）、`report-writing-paper/SKILL.md`、`report-writing-poster/SKILL.md`、`report-writing-slides/SKILL.md` です。共通は内容保持、説明順序、指摘の採否、変更箇所と全文・PDF確認に絞りました。日英の文体・既存の言い換え表19項目・利用者追加の候補は表現へ、図表の指標と数値・検証スクリプト・一次文献の異種AI二重チェック・関連研究の内容忠実性は検証へ移しています。必須確認を減らす変更ではありません。媒体別には構成、説明量、読順、様式とレイアウトを置きます。

初出の定義・説明順序・節のつながり・定期的な通読は全媒体共通の正本にまとめ、媒体別には紙面・掲示・投影・自習の違いだけを置きます。共通作業原則は適用先と作業上の制約を案内し、検査の長い手順を再掲しません。document-checks／related-researchも、完全な検証本文が同じ実行のwriting-rules保存版に含まれる場合は担当固有の指示と固定版への参照に絞ります。旧版・カスタム版で同じ検証本文がない場合は、従来の詳細指示を保持します。別版への読み替えや必須検証の省略ではありません。

表現ルールには指示の出典や取り込み経緯を載せず、不要な強調・定型導入・曖昧な帰属・チャットの残骸を執筆時から避ける指示にまとめています。専門語・引用・数値・不確実性は保護し、AI専用語や自動不合格の辞書にはしません。

保存先は各欄に表示し、プレーンテキストでも編集できます。保存・再読み込み・同梱ルールへの復元は他の欄や未保存入力を変更しません。復元は保存前の下書き操作です。空の指示・不正な形式・保存競合は拒否します。既存のカスタム設定は起動だけでは初期化しません。統合作業で保存版を更新するときは、旧版と提案版のハッシュを検証し、全原文を `before-consolidation-*` にバックアップしてから保存します。未知の旧補足カスタム版があれば内容の確認を求め、自動的に捨てません。過去と実行中の担当の固定版は保持します。

配布物のライセンス表示は指示本文と分けて保持しています。医学著者固有の文体、検出器スコア最適化、固定文長、無条件の置換、CLI直接起動・投稿用スクリプトは導入しません。旧academic／expressionのファイルは動作中の旧アプリとの互換用に保持しますが、新版の編集画面・新しい固定版には読み込みません。

執筆／更新した論文・ポスター・スライド（ノートを含む）・標準報告書について、レポーターの最後の編集工程として適用 → PDF等を再生成・確認 → 独立した2回のレビュー、の順で実施します。修正ループや「レポートのみ」の追加指示でも再適用します。読むだけの相談・レビューや完成済み文書には自動編集しません。スライド専用プリセットの追加ではなく、承認済み成果物にスライドがある場合も対象とする機能です。

作業プリセットとは別に、執筆ルールは書き込み可能な全担当とレポーターの開始時に固定保存し、TeX執筆前から指示に含めます。ローカル・遠隔、すべての作業モード、続行・やり直し・レビューからの修正に共通です。変更は次に開始／再開する担当から反映し、実行中の内容は変えません。Task概要で最終レポーターの適用版・確認結果・使った指示を確認できます。最終レポーターの管理用完了確認に適用版と全対象ソースを要求し、未提出・版違い・未解決事項・登録済み文書の確認漏れでは停止して再開待ちにします。Codex／Claudeではこの結果は管理用通信に送るため、ターミナルへのJSON表示は増やしません。

システム設定は一階層の折りたたみ一覧です。分類名は固定見出しにし、実行設定、共通ルール、モード別設定、媒体別執筆ルール、スキル管理、SSH、TeX・PDF生成を個別に開閉します。項目内の詳細・保存先は再び折りたたまず表示します。閉じても未保存入力は保持し、保存ボタンを押すまで設定を変更しません。操作権限の説明はサービスのヘルプから確認できます。

共通の保存先とSKILL識別子 `de-ai-style` は既存設定との互換性のため維持しています。保存時の共通識別子は `report-writing` も受け付けます。6区分のルールと適用先の指示をまとめて担当開始時に固定し、その組合せ全体の版を完了確認に使用します。実行途中のルール編集で既存の適用確認を無効化しません。未登録のスライドも承認済み成果物なら対象ですが、新しい成果物を勝手に追加する権限は与えません。

管理用通信は結果の種類ごとに最新の提出内容を保持します。仕上げ確認（editorial-check）の後に作業報告（work-check）を提出しても、仕上げ確認は消えません。同じ種類の再提出のみ前の内容を置き換えます。受領だけでは工程を完了せず、CLIの完了通知後に適用版・対象ソース・未解決事項とPDFを確認し、独立レビューへ進みます。

OpenCodeの独立レビューで、結果が受領済みなのに最終行の完了通知だけが欠けた場合、同じ会話・担当・モデルへ通知だけの修正を最大2回依頼します。未取得の指示、不受理のレビュー、ユーザー介入、CLIエラーは自動修正の対象外です。通知が直ってもレビュー判定・証拠の検証は省略せず、不合格を合格に変えません。実装には公式SDKの [session.promptAsync](https://github.com/anomalyco/opencode/blob/dev/packages/sdk/js/src/gen/sdk.gen.ts) を使用します。通知失敗時も管理結果を実行履歴の復旧用データとして保存します。再開時は同じゴール版・担当CLI・モデルの同じレビュー工程にだけ提示し、現在の成果物を確認してから再提出させます。別サービスへの独立レビューには流用しません。

アプリは完了確認と登録済みソースの存在・範囲、既存のPDF検査を行います。文章品質と未登録の成果物の網羅性はエージェントが確認し、レビュワーが実際の成果物を独立検証します。機械検査だけで「AIらしさ」の消失を保証するものではありません。初期ルールは冗長さ・定型的な強調・曖昧な記述の推敲に限定し、事実・引用・数値・不確実性・必要なAI利用開示は保持します。推敲の管理記録は本文には載せません。

### 主担当方式の実行

最初の主担当は、成果物単位の分割、完了までの依存関係、並列化の効果と引継ぎコスト、必要最小限の文脈、利用可能なサービス・残量の鮮度・予算配分を検討します。計画の `coordination` に記録すると「実行計画・体制 → 分担・作業効率の戦略」で確認できます。古い保存済み計画の書き換えは行わず、新しい計画・再計画から適用します。

計画内の `tasks` は、既定の読み取り専用 `investigation` に加え、`kind: "primary-work"` で主担当自身の小さな実装・実験・執筆工程を含められます。各工程に成果物・検証・依存先とトークン見積もりを持たせ、必要なら `estimatedMinutes` を添えます。主担当の最終統合見積もりとは二重計上しません。依存先が完了すると随時次を投入し、無関係な遅い調査と一律に待ち合わせません。見積もった依存経路が長い調査を優先します。実作業工程は既存の読み取り担当が終了してから単独で起動し、その間に別の担当は起動しません。共有ディレクトリの読み書き・ベンチマークの競合を避けるためで、複数ワーカーの並列書き込みや作業ディレクトリ分離はまだ行いません。最終統合、PDF、独立レビューの完了条件は従来どおりです。

Dispatch の「エージェント構成」で主担当方式／従来方式を選択します。新しい主担当方式は、ゴール承認後に主担当が実行計画を提出 → アプリが検証・保存 → 必要な専門担当を実行 → 主担当が実作業・統合・自己確認 → レポートビルド → 独立レビュー、の流れです。専門担当0人の計画も可能です。主担当の計画と実作業は別の完了境界を持ちますが、対応CLIでは保存済みの会話を引き継ぎます。計画だけでゴール達成とは判定しません。進捗確認専用のプランナーは通常起動しません。主担当の構造化された自己確認と既存根拠ファイルを検査し、未完了・ユーザ確認・不正な応答ではそのままレポーターへ進めません。自己確認は達成判定ではなく、最終レビューで成果物を別途検証します。

「計画後に承認を待つ」は、主担当の実行計画を保存した直後、専門担当や実作業を始める前に停止します。計画担当CLIを明示した場合だけ、別の読み取り専用計画工程も追加します。開始済みの構成を変更して承認を迂回することはできません。既存タスクの現在の工程は移行せず元の構成を維持します。主担当方式の「修正・続行」は新しいラウンドの計画から始まります。相談・レビューのみ・レポートのみの追加指示にはこの計画工程を挟みません。

タスクの「実行計画・体制」タブで、方針、変更理由、担当ごとの成果物・検証・対応する達成条件・依存関係・見積もり・実際のCLI割当と状態を確認できます。計画は各ラウンド最大4版（初期計画＋3回の更新）。主担当は新しい知見や検証結果に応じて計画を更新できます。分担の実行失敗・利用不可では全実行中分担の終了を待ち、成功成果を残して未完了分担を履歴へ撤回し、主担当へ再計画を戻します。レート制限にはまず既存のルーティングで代替CLIを試します。再計画上限到達、解消できない予算不足、自動修正後も不正な計画では確認・再開を待ちます。ユーザの手動停止は自動再計画・自動再開しません。通常の計画変更は自動適用しますが、ゴール・予算・権限は変更できません。介入は一時停止後の追加指示を使います。計画と撤回した工程・実行ログは保存され、PDFには載せません。

実行計画は実作業前に必須検証します。CLI起動前に承認済み達成条件IDと戦略設定を確認し、計画担当に使用可能ID・分担数・残り予算を明示します。管理用通信の提出時にも同じ検証を行い、欠落項目・型・未知のID・担当漏れ・依存関係・予算超過を具体的に返して同じセッションで修正させます。CLI終了後に不備が残った場合も、実作業に進まず同じ計画工程を最大2回まで自動修正します。修正は計画の版数を消費せず、ログと不受理案を保持し、通常の予算・一時停止を尊重します。作業量見積もりの固定10万tokens上限はありません（500以上の安全な整数）。未指定予算には架空の上限を設けず、指定したタスク予算は維持します。見積もりの過少申告やゴール・権限の自動緩和は許可しません。

主担当方式では全工程の長い引継ぎを配布せず、直接依存する工程の要約（設定に応じて合計最大16,000文字、各分担に均等配分）と成果物・必要時に読む外部ログを渡します。省略前の関連入力とユーザ指示履歴はアプリデータの `contexts/<task-id>/<run-id>.json` に保存し、必要時に参照します。最終レビュワー用の入力には作業者の成功主張を含めません。可能なら作業者と異なるプロバイダをレビューへ割り当てます。明示した担当指定は尊重します。

PDFビルド担当は既存の自律修復を維持するため、独立したCLIとして毎回実行します。

### 仕上げ前の内容改善

実装・解析・着想に不確実性がある場合、主担当は初期成果に対する代案・弱点・ボトルネックを利用可能な別AIへ分担し、有用な提案を実作業と評価へ戻す計画を優先します。単独の課題でも「初版 → 独立した改善提案 → 主担当の試行・比較 → 統合」の依存グラフを使えます。初回の独立案は他候補の結論を見ずに固定し、その後の検討で共有します。単純な修正、有用な分担がない場合、残り時間・使用枠が少ない場合は単独作業も可能です。

任意の計画項目 `refinement` は改善対象 `objective`、通常の検討工程キー `proposalKeys`、反映工程 `applicationKey`（省略時は最終主担当）、追加探索を区切る目安 `stopWhen` を持ちます。アプリは工程の存在と依存関係を検証し、反映工程が提案の完了前に始まらないようにします。採否・根拠・改善前後は既存の作業報告へ残し、専用の提出書類や合否ゲートは増やしません。「分担・作業効率の戦略」に改善対象と担当を表示します。

同梱 `content-refinement` スキルはスキル管理で編集できます。最終レポーター・レビュワー、相談・レポートのみのラウンド、専用の読者検討を持つ解説スライドには配布しません。目安時間内では内容の洗練を優先し、変更していない機械検査は保存済み根拠を確認して再利用します。必須の実験・文献照合・PDF確認・独立レビューは省略せず、既存計画・実行中工程の保存版は変更しません。

### 会話継続・分割・負荷分散・並列実行（段階2〜5）

「システム設定 → 実行の基本設定」は新規タスクの既定値専用です。通常は割り当て方針・レビュー方式・最大同時実行数・トークン予算目安を表示し、会話引継ぎ・必要時の分担・最大分担数・文脈切替量は詳細設定にまとめます。保存済み値を勝手に変更しません。既存タスクの変更は、そのタスクの概要にある「実行戦略を設定」で専用画面を開きます。停止中のみ変更でき、システム既定値とは独立して保存します。

- 会話継続：CodexとClaude Codeの完了フックから正確なセッションUUIDを記録します。同じタスク・主担当・CLI・指定モデル・ゴール版の成功済み会話だけを、対応CLIのネイティブfork機能で引き継ぎます。元端末の画面・ログは保持しますがプロセスは終了し、新しい端末がその文脈から続けます。計画からの実行、分担からの統合、修正、追加作業、アプリ再起動後にも利用できます。失敗・途中終了で有効なIDがない場合、モデル変更、文脈量超過、引継ぎ無効時は成果物と引継ぎから新規会話を開始します。独立レビュー・明示した別プランナー・専門担当・ビルドは独立会話です。復元先の記録をCLI側で削除した場合はエラーを表示し、会話引継ぎを無効にして再開できます。Claudeの現行の新規会話方針は下記を参照してください。
- 作業分割：新規の主担当は `<execution-plan>` で全体方針、変更理由、主担当の残作業、専門担当の成果物・検証方法・承認済み条件ID・依存関係・見積もりを提出します。必須条件の担当漏れ、循環、重複ID、未知の条件、書き込み指定、上限超過を拒否します。計画中の作業禁止は主担当への指示であり、主担当自体の書き込み権限を新たに制限するものではありません。専門担当は読み取り専用の実行モードです。既存の未移行工程は従来の `<work-plan>`（1修正サイクルに1バッチ）を維持します。AIの自己申告は最終合格ではありません。
- 並列実行：依存関係が満たされた読み取り専用の調査・検証を、空き枠に随時投入します。効率重視では利用可能な複数サービスへの分散を優先し、通常方針の独立調査はCodex／Claude Codeを候補とします。編集・実験は主担当の単独工程に集約し、共有書き込みの並列化はしません。停止・失敗時は新規投入を止め、実行中作業が落ち着いてから中断処理または再計画へ進みます。再開時は成功済みの分担を保持します。同じCLIの複数端末も「並べて表示」で同時に見られます。
- 割当：利用枠、鮮度、同じ契約先の実行中予約、優先度、タスク内の直近のCLI実行失敗率、会話継続の利益を使う説明可能なルールです。不明・10分以上古い使用率は空き0%と見なしません。リセットが近いことは小さな選好にのみ使い、実際のクールダウンは守ります。主担当への固定指定を独立分担すべてへ流用しません。学習済みのタスク適性モデルや最適化アルゴリズムではありません。
- 予算：ゴール整理を除き、全作業回・修正・再開を累積します。入出力の両方が報告されていればその合計、未取得なら工程別見積もりとプロンプト／返答の文字量から推定し、GUIに推定を含むことを表示します。端末のANSI描画量を実トークン量とは扱いません。初期見積もりは主担当8,000、ビルド3,000、レビュー5,000で、分担は提案値を使用します。非表示のツール応答・推論・CLI内部処理を完全には計測できず、**厳密なトークン上限や課金上限ではありません**。残量不足では新しい実作業・修正・分担の着手を保留します。PDF・最終レビューの余力を予約し、これらは推定超過後も実行します。予算を調整して明示的に再開できます。時間・推定量による実行中CLIの強制終了はしません。

実CLIの会話継続を検証する任意テストは `node scripts/smoke-continuity.cjs codex` と `node scripts/smoke-continuity.cjs claude` です。それぞれ少量の利用枠を使う2往復のテストで、ファイル操作は指示せず、2番目のプロンプトに書かれていない内容を前の会話から復元することを確認します。実行にはインストール済み・ログイン済みCLIが必要です。

### 敵対的レビューの交互実行・2回連続合格と自律修正

標準の流れは「作業 → 進捗確認 → TeX/PDFビルド → 敵対的レビュー → 判定に応じて修正または次のレビュー」です。常に直前のレビューとは異なるCLIを使い、各レビューは新しい読取専用の会話で実行します。作業担当と別CLIを優先しますが、候補不足ならワーカーのCLIも利用します（作業中の会話は引き継ぎません）。次のレビュワーへ前の判定をプロンプトで渡しません。反証・境界条件・不足する検証・PDFの問題など、実際の根拠に基づく指摘を求めます。

同じ成果物で必須条件が2回連続合格し、追加検討事項もない場合だけ完了候補です。不合格・未検証、あるいは合格でも追加検討事項があれば、その時点でワーカーへ戻して修正・再ビルドします。連続合格数はリセットしますが、直前のレビューのCLIは引き継ぎます。例：「Claude合格 → Codex不合格 → 修正 → Claude合格 → Codex合格」で完了候補です。最初のレビューが不合格なら、その時点で修正に戻し、既知の不合格成果物をさらにレビューしません。新規タスクでは自律修正を標準で有効にします。最大修正サイクルは初回を含む1〜5回（初期3回）で、レビューそのものの通し番号とは別です。自律修正を明示的に無効にすると、問題発見時はユーザ判断待ちになります。権限や範囲の確認は自動で解決せず停止します。

少なくとも2種類の利用可能・認証済みCLIが必要です。3種類目が利用可能なら執筆に参加していないCLIを優先します。ワーカーのCLIまで候補に含めても直前のレビューとは別のCLIがない場合は待機し、隣り合うレビューの別CLI条件は緩和しません。Goalの「利用CLIを変更」で候補を追加し、中断工程から再開できます。レビュワーの固定指定はタスクの最初のレビューに適用し、以後は修正や追加作業を挟んでも直前とは別CLIを自動選択します。レポーターは自動割当ならワーカーと同じCLIを優先します。

既存の承認済みタスクは次の実行・再開時に2レビューへ移行します。ゴール未設定の旧タスクは実行を止め、「別タスクに分ける…」で引き継いでゴールを承認してから進めます。旧タスクを合格済みとみなして完了させることはできません。

レビューは全条件の合否、確認内容、根拠ファイル、追加検討事項を構造化して返します。アプリは条件ID・ゴール版・必須情報と実際の担当CLIを検査し、根拠ファイルおよび登録済みの全TeX/PDFをハッシュ付きで記録します。ファイル不在、レビュー中・レビュー間の変更、根拠不足では合格にしません。完了操作時にも両レビューの証跡を確認します。ハッシュは版の証跡であり、説明の正しさを機械的に保証するものではありません。

レビューの必須項目（`concerns` 配列を含む）は `submit_result` の提出時点で検証します。形式不足は同じエージェントに具体的な修正点を返し、指摘・判定・根拠を維持して再提出させます。ローカル／SSH先とも同じ検証処理を使います。欠落した `concerns` を勝手に空配列へ補完しません。拒否された下書きも復旧用に保持し、過去の合格回答を代わりに採用しません。CLIが形式修正前に終了した場合は同じレビュー工程を最大2回自動再試行し、修正サイクル・レビュー合格数には加算しません。通常の予算・CLI利用制限は維持します。

回数上限、必須条件の改善が連続して見られない場合、ユーザ判断が必要な場合、構造化レビュー自体の欠落や自動修正後も不正なレビュー、PDFビルド失敗では停止して未達内容を表示します。時間によるCLIの強制終了は行いません。トークン上限を保証する機能ではありません。既存の成果物・履歴を残し、追加指示で修正を再開できます。「レビューのみ」は読取専用で再評価し、成果物の自動修正は行いません（レビュー提出形式の修正は行います）。

進捗確認の形式不備や根拠パスの検証失敗は、担当の読取／書込権限を維持したまま同じ工程へ自動で再提出を依頼します（追加2回まで、通常の予算判定は適用）。`work-check.evidence` は1項目につき実在ファイルのパス1つだけです。説明や複数パスを混ぜた文字列は推測で切り詰めず、担当が実物を確認して修正します。本当に成果物が不足する場合は `needs-work` で既存の自律差戻しへ戻します。通常の修復はユーザ確認不要と指示しますが、承認範囲・権限・接続・予算や明示された停止は勝手に変更しません。再提出でも受理できない場合は成果物を保持して同じ工程から再開できます。

### 作業目安時間と役割分担

Goalの「作業目安時間」に全工程合計の分数を設定します。空欄は未指定です。プランナーはこの目安に合わせ、ワーカーに主な時間を配分し、成果物・検証方法・中間目標を計画します。全担当へ実行済み時間と目安を渡し、必須条件を守りつつなるべく目安付近で完了させます。時間超過は許容し、超過を理由に終了・キャンセル・合格扱いにはしません。休止中・ゴール整理中の時間は実行時間から除きます。再開も同じ作業回の累計に含めます。

プランナーは計画とワーカー後の進捗確認、ワーカーは調査・分析・実装・根拠収集・TeX本文と図表、レポーターはビルドと体裁修正、レビュワーは独立検証を担当します。ワーカーのTeX編集は状態更新時にも保持します。進捗確認は通常の対話CLIで読取専用実行し、元の計画担当が利用可能なら優先します（別セッションで引継ぎを渡します）。実行中の継続監視は経過時間通知、AIによる再計画はワーカーの引継ぎ時点です。並行AIが常時監視・端末入力する仕組みではありません。

プランナーは根拠ファイルと残作業・見込み時間を返します。許可済み範囲の不足は自律反復が有効ならワーカーへ戻し、無効なら追加指示待ちにします。制約の矛盾・権限不足はユーザ確認待ちです。不正な進捗回答や根拠ファイル不在ではレポーターへ進みません。差戻しは最大レビュー回数を作業試行の上限にも使用し、上限では判断待ちにします。ファイル存在検査は内容の正しさを保証せず、最終レビューも別途必要です。既存の承認済み制約を自動解除することはありません。

### 途中終了からの再開

作業目安時間は停止条件ではありません。超過後も必要なレポートと最終レビューへ進めます。CLIの終了やビルド失敗、構造化レビューの取り込み失敗、ユーザによる一時停止、アプリ再起動などで途中終了した場合は、タスク上部の「中断した工程から再開」を押します。新しい作業回を作らず、完了済みの前工程、TeX・PDF・外部ログを保持して、その工程と必要な後工程だけを実行します。再試行した成果物に依存する古い後工程の検証結果は無効にして再検証します。

CLI自体は新しい対話セッションとして起動することがあります。保存ファイル、前工程の引継ぎ、中断時のログの場所から残作業を確認するよう指示します。CLI内部の会話メモリそのものの復元を保証するものではありません。履歴には再開回数と再開前の記録を保持します。再開は明示操作で、勝手に実行を再開しません。保存済み追加指示がある場合は、先にその指示を実行するか破棄してください。

制約の矛盾・許可不足などユーザ判断が必要な停止、検証不合格や反復回数上限は単純再開で飛ばせません。回答・方針変更を「追加指示」から与えてください。途中再開可能な工程が残るタスクは完了扱いにできません。

### 使用量の取得制限とCLI通知

Claudeの直接取得APIがHTTP 429を返す場合は、モデル利用枠切れとは別の「取得要求の制限」として扱います。Retry-Afterと段階的な待機時間を尊重し、待機状態を保存するため再起動やRefresh連打で再送しません。通常取得の短時間重複も抑えます。OpenAIとAnthropicの取得は並行し、一方の失敗で他方の更新を止めません。

このアプリから起動するClaudeには、その起動に限るstatusLine通知を設定し、Claudeが提供する利用枠を外部APIへの追加要求なしに受け取ります。ユーザの設定ファイルは変更しません。通常のClaude作業によるモデル消費は発生します。CLIが通知しないモデル別枠は削除せず、取得時刻付きの前回値として残します。APIの制限そのものはアプリ側で解除できず、通知もまだない場合は以前の値または不明を表示します。`node scripts/smoke-completion.cjs --status`は少量のCLI利用枠を使い、短い応答1回と実際の使用量通知を確認する任意テストです。

検証: `npm run build && npm test`、`npm run test:layout`。`node scripts/smoke-completion.cjs --goal`は少量のCLI利用枠を消費する任意の実機テストで、Codexに短いゴール案を1件だけ提案させて構造化回答を検証します。

### 結果を確認しながら反復する

作業終了時はタスク全体を閉じず `結果の確認待ち` になります。各タスクの下部で追加指示を入力し、`続ける` を押すと、前回の成果物と履歴を保持して次の回を開始します。既存の完了・失敗タスクでも利用できます。

途中の確認事項（例：Git作者の指定）への回答は、新しい作業回ではなく**停止した工程の続き**として実行します。`回答して続行`／`指示を渡して再開` は、承認済みゴール・既存計画・工程ID・依存関係・完了済み担当・実行ログ・経過時間を保持し、必要な工程だけを再開します。回答は「作業履歴」の「途中再開時の回答・指示」に保存します。合格条件や操作権限は回答だけでは変更せず、明示的な変更・承認が必要です。完了後の追加作業、相談・レビューのみ・レポート更新、明示的な作業範囲変更は別の作業回になります。

依存グラフ・実績タイムラインは、過去の作業回がある場合も既定で「タスク全体」を表示します。「今回の作業のみ」に絞ることもできます。過去の未着手工程は保存時点の計画として区別し、現在の待機列や完了扱いにはしません。回をまたぐ依存関係は推測で追加せず、タイムラインは保存された実行記録だけを使います。確認・停止中の空白時間は実作業時間に含めません。

- `修正・続行`：修正→TeX/PDF更新→独立した敵対的レビュー2回。計画後の確認を有効にすると、その前に計画→承認待ちを挟みます。
- `相談・計画`／`レビューのみ`：読取専用で結果を返します。成果物・作業中のTeX/PDFは更新しません。結果は `作業履歴` で確認できます。
- `レポート更新`：既存TeXに追加指示を反映してPDFを再生成します。
- `次回用に保存`：実行中でも追加指示を保存できます。自動実行や実行中の指示変更はしません。一時停止後または作業終了後に開始してください。
- `担当CLI・モデル／計画後の確認`：役割別にCLIとモデルを指定できます。自動なら修正担当は前回の担当を優先し、レビュー2回は互いに別CLIにします。作業担当とは別CLIを優先しますが、候補不足なら同じCLIの新しい会話を使います。代替CLIを許可しない固定担当が使用できない場合は待機します。代替へ切り替えた際は、別CLIへ固定モデル名を持ち越さずそのCLIの設定を使用します。
- 初回実行前や一時停止中は、同じ設定欄の `現在の工程に担当・確認設定を適用` で現在の工程にも設定できます。計画は `作業履歴` で読み、`計画を承認して続行` で進めます。
- 確認待ちのタスクは他のキュー実行を妨げません。最終確認後、`タスクを完了にする` を押します。

各回の終了時（または中断した回から次の回を開始する前）に、TeX本体と生成済みPDFをレポートディレクトリの `versions/` に保存します。Reportの版選択で過去のPDFを確認できます。相談・レビュー回の版は変更していない直前のレポートです。コードや外部画像を含む作業領域全体の巻き戻し機能ではありません。CLI会話の再開に依存せず、元の目的・直近の追加指示と引き継ぎ・現存ファイルを次の担当へ渡します。全履歴はアプリに保持し、CLIへ渡す履歴量は上限を設けています。

PDF・ターミナルはウインドウの残り高さに合わせて自動伸縮します。実行画面の工程・担当欄は展開式です。

Report内のPDFはローカルのPDF.jsビューアで表示します。「ページ一覧」と本文の間の境界を左右にドラッグすると左ペインの幅を変更できます。幅は保存され、ダブルクリックで既定幅に戻せます。境界にフォーカスして左右キーでも調整できます。ページ一覧・目次、倍率変更、本文検索（Enterで次・Shift+Enterで前）、テキスト選択、PDF保存に対応します。PDFは選択したタスク・版のファイルだけを読み込み、外部へ送信しません。

レポート本文は依頼された主題の背景・方法・結果・考察・検証・参考文献に限定します。担当エージェント、CLI・モデルの割当、使用量、タスクID、実行状態・日時、作業パス、ワークフロー、生成処理の説明は掲載しません（それら自体が依頼された調査対象の場合を除く）。新規TeXのひな形にも管理情報や架空の著者は入れず、レポート更新時は既存の不要な管理節も除去するよう指示します。運用情報はアプリの作業履歴と外部ログに保持します。

### CLIそのものを操作する

新しい実行はすべて対話PTYで起動します。`Execution` の端末内をクリックして通常どおり入力してください。CLIのスラッシュコマンド、承認ダイアログ、キー操作はそのCLI自身が処理します。別の監視用シェルやJSON表示ではありません。CLIの起動引数でタスクを渡すため、起動直後にCLIの信頼確認・ログイン・権限確認が出る場合も、その端末で対応してください。

- エージェントタブで切替、`並べて表示` で複数CLIを同時表示。セッション選択で同じ担当の過去の実行にも戻れます。
- タブ切替や画面再読み込みではCLIを再起動しません。通常のターミナルのスクロールと、保存された外部ログを利用できます。
- 独自の画面履歴・監視用画面の記録は行いません。以前の外部ログと画面記録ファイルは削除せず保持します。Claude・Antigravity起動時の限定的な信頼確認だけは、履歴を保存しない内部処理で維持します。
- Codex・Claudeでは、最初の表示は短い開始指示にし、詳細な工程指示は実行専用の `get_instructions` ツールで取得します。計画・判定などの管理用JSONは `submit_result` でアプリへ提出し、最終回答は通常の文章にします。CLI自身のツール詳細を展開した場合はJSONが見えることがあります。コード例や成果物として必要なJSONは隠しません。端末の生データを文字列判定で削除する方式ではありません。
- 専用接続はその実行の指示取得と結果提出だけに限定し、任意のファイル操作や外部通信は提供しません。提出だけでは工程は進まず、従来の完了通知と役割別の検証が必要です。Geminiは従来の回答方式です。OpenCodeもこの専用接続を使い、実行専用プラグインから完了を通知します。
- Codex・Claudeの工程完了は、それぞれ `notify`／`Stop` フックが返す最終回答と実行固有の完了マーカーで判定します。エージェント自身には通知ファイルを書かせません。MCPの初期化と今回の指示取得は別々の受領記録で確認し、接続しただけでは完了できません。ネイティブ最終応答で指示取得が未確認、または有効な完了通知が欠けた場合は、理由付きの再開可能な停止にします。承認待ちや途中報告・子エージェントの応答では判定せず、フック自体が禁止・故障して通知できない場合は手動の一時停止が必要です。Claudeの `StopFailure` が返す使用枠不足も自動ルーティングに使います。
- 担当交代は「最終通知の受領 → 元CLIの入力・管理操作を無効化 → CLI終了確認 → 次の担当」の順です。完了・認証失敗・使用枠超過のいずれも、前のCLIを入力可能な状態で残しません。遠隔では実行固有の停止要求と終了記録・ロック解除を照合します。確認できなければ自動引継ぎ・再計画を保留し、手動再開時にも再確認します。画面とログは閲覧可能です。認証は専用ログイン管理で行い、回復しても古い担当は復活しません。SSH接続と投入済みバッチジョブはこの担当交代では終了しません。これは作業時間制限ではなく最終通知後の終了処理です。
- ClaudeはMCP接続情報を工程間で持ち越さないため、新規会話を使用します。成果物・要約・保存ログは引き継ぎますが、CLI会話の分岐は行いません。Codexの互換性確認付き会話分岐は変更しません。
- 遠隔の実作業とTeX本文が完成し、残りがPDFビルド・体裁修正・全ページ確認のみなら、主担当は `work-check` の `report-ready` を提出します。根拠ファイルとレポートTeXの存在を検証し、残作業を待機中レポーターへ渡します。標準設定ではMacで実行し、仕上げ検証と2回の独立レビューは省略しません。`needs-work` や `ask-user` を文章の推測だけで読み替えることはなく、旧実行の判定を自動変更しません。
- ローカルCodexとサンドボックス設定の遠隔Codexは `--ask-for-approval never` と読取専用／workspace-writeサンドボックスを併用します。書込工程では通常の依存取得・調査に必要なネットワークを有効にし、作業フォルダと当該タスクのレポートフォルダを許可します。禁止された操作は自動承認せずエラーとしてエージェントへ返します。新規の遠隔接続先はFull accessを初期選択し、リスク確認後に保存します。Full accessの遠隔タスクは全Codex工程でサンドボックスを使用しません（読み取り制限も指示のみ）。既存接続先・タスクは従来の権限を維持します。Claudeはユーザ指定により、ローカル・遠隔の全担当を `--permission-mode bypassPermissions` で起動します。通常の操作承認なしにファイル変更・コマンド実行でき、計画・レビューの読み取り制限は指示のみです。専用の作業環境を推奨します。ハーネスが起動するCLIに限定し、保存設定・組織ポリシーは直接書き換えません。起動済みCLIには遡及せず、アプリ再起動後の新しいCLI起動から適用します。
- Claude・Antigravityの起動時の信頼確認は、上の「CLIの初回フォルダ確認」の範囲で自動承認します。ホーム起動ではホーム全体が信頼対象になるので、専用プロジェクトフォルダを推奨します。手動入力・指示取得・通常CLI画面への移行後は自動回答せず、起動済みCLIにも遡及しません。
- Antigravityなどのファイル連携CLIでは、管理結果を `--submit`、通常の日本語の要約を `--finish` に標準入力で渡します。完了通知はアプリの専用コマンドが担当識別子付きで作成するため、CLIは通知JSONを手書きしません。必要な結果が未提出・未受理なら理由を返し、工程は進めません。不正な通知が残った場合は実行画面に原因を表示し、Antigravityの既知の入力待ち画面でのみ、提出形式の修正を最大2回促します。手入力・一時停止があれば自動入力は止めます。成果の再作成や未確認事項の合格化は指示しません。通知の受理後も従来の品質検証と旧CLIの終了確認を行います。
- 通知されないときの救済として `工程完了・引継ぎ` も残しています。OpenCodeはネイティブの `session.idle` / `session.error` イベントを利用し、実行固有の初回指示とルート会話を確認してから通知します。
- 工程完了後も端末は操作可能です。ただし後続担当が同じ作業領域を使います。過去のCLIに並行して変更を指示しないでください。不要なら `端末終了` で終了できます。
- 工程・担当欄と下部の追加指示欄の境界をドラッグして高さ調整できます。サイドバーの境界・並列端末の中央境界は幅を調整します。境界をダブルクリックすると既定サイズに戻ります。
- アプリ自体を終了するとローカルPTYも終了します。遠隔CLIの終了は接続断だけでは確定しないため、再起動で中断した遠隔実行には終了未確認の印を保存します。SSH再接続・同じ工程からの再開時に、既存の終了確認・実行ロック照合を通してから次を起動します。確認不能なら停止を維持し、完了済み成果や分担計画は保持します。tmuxで保持した遠隔CLIは、同じ最終マシンへSSH再接続して同一工程・実行IDへ戻します。アプリ終了だけでは保持したCLIを停止せず、次の工程も開始しません。明示的な一時停止・担当切替では終了確認を必須とします。画面再読み込み用のメモリ内出力は直近1 MiB、外部ログは全出力です。過去の保存出力は終了時のスナップショットです。
- `Pause workflow` は現在のCLIを終了し、未完了工程を保留します。`Resume workflow` は引継ぎ情報と現存ファイルで同じ工程を新しい対話セッションとして再開します（プロセスの凍結・解凍ではありません）。

左サイドバーには取得できた使用枠をすべて表示し、各枠の使用率とリセット日時（ローカル時刻・タイムゾーン付き）を確認できます。Claudeは `Current session`、`Current week (all)`、サーバーが返すモデル別週次枠（例：Fable）を表示します。日時が返されない枠は推測せず `Reset: not reported` と表示します。クリックするとモデル別詳細が開きます。

実行中に `Pause workflow` を押すと現在のCLIだけを安全に停止し、後続工程へは進みません。停止後は `Resume workflow` で同じタスクを続行できます。

作成済みタスクは右側のタブで切り替えます。停止中のタスクは詳細画面の `Delete task` から削除できます。実行中は停止するまで削除できません。

`balanced` は優先度と使用率の両方、`quality` はCLI優先度、`quota-saver` は使用率と累積トークンを強く見て担当を決めます。Reviewは、可能ならExecuteと異なる契約先へ割り当てます。

## 作業の続行・最初から・別タスクへの分岐

通常はタスク下部の「進め方」を「成果を使って続ける」のまま、追加指示を書いて「続ける」を押します。同じタスク内に前回の履歴を保存し、次の作業を始めます。相談・レビューのみ・レポート更新もこの欄で選べます。

同じ欄の「同じゴールで最初から…」「別タスクに分ける…」は、確認画面を経て新しいタスクを作る操作です。選択だけでは作成も実行もしません。元タスク・ファイル・ログを削除せず、入力中の追加指示も元タスクに保持します（新タスクへの追加指示は作成後に入力）。新しいタスクは作成直後は未実行で、確認してから開始します。未承認ゴール・旧形式タスクには上部の「別タスクに分ける…」を残しています。実行中は分岐できず、遠隔タスクは空フォルダからの再作成を選べません。

- **別タスクに分ける**：作業フォルダを共有し、報告書フォルダのTeX・図表・追加成果物を新タスクの保存先へコピーします。前回の指示・工程結果・外部ログへの参照を短い引き継ぎ情報として渡します。報告書の過去版、ログ、フォントキャッシュはコピーしません。共有フォルダを元タスクと同時に操作しないでください。
- **同じゴールで最初から**：アプリのユーザデータ内 `workspaces/<新タスクID>/` に空フォルダを作成します。元コード・前回成果物も自動コピーしないので、必要な入力を用意してください（論文解説モードの登録PDFは引き継ぎます）。Gitの巻き戻しや既存フォルダの削除は行いません。ゴールに以前の絶対パスが書かれている場合は、実行前に新しい入力・出力先との整合を確認してください。

両方式ともゴールの本文・承認状態・変更履歴、作業プリセットの固定版、CLI／モデル／担当設定、実行・自律反復・予算設定を引き継ぎます。計画・工程・会話・評価・使用量は新しく始め、前回の合格判定は使いません。アカウント全体の契約使用量はリセットしません。「中断した工程から再開」は従来どおり同じタスクの未完了工程を続ける操作です。

## 再作業上限での自動仕上げ

同じ担当の再作業が上限に達した場合は、未達・未確認事項を保持したまま、部分成果のTeX/PDF作成と独立レビューへ進みます。研究モードのアイディア・関連研究・実装段階でも適用します。前提が満たせない後続の未着手工程は「未実施」として履歴に保存し、完了扱いにはしません。レビュー後は残課題付きの作業終了となり、自動で同じ修正ループへ戻りません。

権限変更の確認、接続障害、実行中の別担当などはこの仕上げ処理で無視しません。旧版で「差戻し回数上限」で停止済みのタスクは、更新後に「残課題を記録して仕上げへ」を一度押すと、保存済みの結果から仕上げへ移れます。アプリ起動だけで停止中のタスクを自動再開はしません。

## テスト

直近の整理内容・再現した不具合・検証範囲は [実装点検記録](IMPLEMENTATION_AUDIT.md) を参照してください。

```sh
npm run build
npm test
npm run test:restart-runtime
npm run test:pdf
npm run test:documents
npm run test:layout
```

`test:restart-runtime` はアプリに同梱されたElectronのNode環境で、やり直し・ワークフロー連携のテストを実行します。通常のNodeとのファイルコピーの挙動差も確認します。GUIテストでもやり直し時の報告書・図表コピーを実行します。

ネイティブ完了通知の実CLIテストは任意です（Codex・Claudeで短い応答を生成するため使用枠を消費します）。`node scripts/smoke-completion.cjs` は読取専用の応答・引継ぎ、`node scripts/smoke-completion.cjs --write` は許可した一時フォルダ内のファイル作成・読取・引継ぎを確認します。テスト用ファイルは終了時に削除します。

通知方式の参照: [Codex notify](https://learn.chatgpt.com/docs/config-file/config-advanced)、[Claude Stop / StopFailure](https://code.claude.com/docs/en/hooks)。

管理データ分離の実CLIテストは `node scripts/smoke-result-channel.cjs codex` または `node scripts/smoke-result-channel.cjs claude` です。少量の使用枠を使い、専用ツールでの指示取得・結果提出・文章による完了通知を確認します。`--write` を付けると、一時フォルダのファイル1つの作成・読取も確認します。接続方式は [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) と [Claude MCP](https://code.claude.com/docs/en/mcp) の公式仕様に従っています。Claudeの計画モードでは、[PreToolUse](https://code.claude.com/docs/en/hooks#pretooluse-decision-control) で形式検証を通った当該実行の管理結果提出だけを許可します。任意の操作や別ツールには許可を返さず、CLI側の明示的なask/denyルールも引き続き適用されます。

既定のタスク保存先は `~/Documents/Agent Harness Reports/<task-id>/` です。遠隔タスクのTeX・PDF・図表・検証証拠は、その下の専用 `artifacts-<id>/` にまとめます。エージェント別の外部ログ（タスク直下の `logs/`・`all-agents.log`）とレポート履歴（タスク直下の `versions/`）は成果物の外に保持します。成果物内の同名フォルダは実験証拠として使用でき、TeXからの相対参照もそのまま転送されます。既存の遠隔タスクは原稿と素材を新しい成果物フォルダへコピーして移行し、元ファイルや内部ログは削除しません。ローカルのみの既存配置は変更しません。TeX引数と作図ツールの検査引数はGUI上で一行に一つずつ入力します。公開版のIPSJテンプレートは個人領域へ公式配布を取得します（[手順](installation.md)）。

## 現在の境界

### 指示書の全文表示・TXT書き出し

各タスクの `実行計画・体制 → 指示書の全文表示・TXT書き出し` から、保存済みのゴール、元の依頼と追加指示、タスクに保存された作業プリセット・共通ルール、実行計画と担当別の指示、予算・反復・環境設定、レポート執筆ルールを読み取り専用で確認できます。未承認のゴール・計画、未実行の追加指示、次回起動用の現在の執筆ルールは明示して区別します。未保存の編集、CLIが保持する認証情報、起動時の通信制御情報は含みません。担当別本文は取得時点の保存状態から構成したもので、過去のCLIへの送信内容そのものではありません。

`TXTで書き出し` は保存先を選んで表示中と同じ内容をUTF-8で保存します。表示中にタスクが進行しても書き出し内容は変わらず、`表示を更新` で最新状態に切り替えます。表示・書き出しだけではタスクやエージェントは起動しません。

### CLIログイン管理とレポート停止の確認

- 通常のログイン画面の操作は「CLIを開く」「状態を更新」「閉じる」です。画面を開いた時と「状態を更新」でCLI検出・認証設定を自動確認するため、検出専用ボタンはありません。「状態を更新」はCodex・Claudeの使用量取得、Antigravityの記録済み残量の読み直しも行います。OpenCodeは選択した接続先の設定確認のみで、Ollama CloudのWeb使用量連携は別です。Claude・Codexのログイン操作が正常終了した場合も使用量を再取得します。ログイン成功と使用量取得成功は別に表示します。
- 個人向けGoogleサブスクはResourcesのAntigravityサービスにある「CLIを開く…」（認証エラー時は「認証を確認…」）からログイン管理を開きます。公式CLI `agy` のGoogleアカウント認証を完了し、タスクの利用CLIでAntigravity CLIを選択してください。既存のGemini設定・実行履歴は変更しません。公式手順: https://antigravity.google/docs/cli/install/
- Antigravityはネイティブ対話画面で実行します。タスクでは操作承認を省略するため専用環境を推奨します。認証情報は公式CLIが管理し、ハーネスはキーチェーンを読み取りません。API方式への切替は行わず、API方式・不明な設定では起動を止め、追加クレジット利用が有効な場合はタスク開始を止めます。CLIの `/settings` で追加クレジットを無効にしてください。
- Antigravityのログイン管理で「閉じる」は画面のみを閉じ、端末と認証を継続します。再表示すると同じ端末に戻ります。「端末を終了」は全CLIで端末の起動中だけ表示し、その端末を終了しますが保存済みログインは消しません。Claude・Codex・OpenCodeのログイン端末が動作中に閉じる場合は終了確認を行います。アプリ終了時は端末も終了します。
- Antigravityの「使用量表示を設定」は未設定時だけ表示します。設定済みかは実際の設定ファイルで確認し、前回の残量があるだけで設定済みとは判断しません。このMacのAntigravity公式 `statusLine` を設定し、元の設定を `settings.json.before-harness-usage` に初回のみ保存します。起動中のCLI設定は変更せず、既存のカスタムstatusLineも上書きしません。既定のCLI表示は維持し、モデル・共有枠の残量とリセット時刻、観測時刻、プラン名だけをローカルに保存します。認証情報・メール・会話本文は保存しません。CLIを起動し、最新値が必要な場合は `/usage` を実行してください。ハーネスは5秒ごとに観測結果を取り込みますが、バックエンドへの定期問い合わせではありません。端末を終了した後は前回値と「CLI観測」時刻が残ります。未報告の枠やモデル対応関係は推測しません。SSH先はResourcesの対象環境から設定します。公式仕様: https://antigravity.google/docs/cli/statusline/
- Gemini CLIはハーネスからの検出・新規起動・ログイン管理・割り当てを廃止しました。過去の実行履歴・成果物とCLI自身のインストール・認証ファイルは保持します。旧タスクでGeminiだけに担当を固定している場合は、停止中に担当をAntigravityなどへ変更してください。異なるCLIのモデルID・認証は自動移植しません。

### GUIでモデルを選ぶ

サービスごとのカードに利用ON/OFF・モデル・ログインを集約しました。「サービス設定を保存」で利用可否とCodex・Claude・Antigravityの既定モデルをまとめて保存します。OpenCodeの接続先・モデルだけは、安全な切替確認のため専用フォームの「OpenCodeに適用」で別途保存します。通常のログイン管理は保存済み接続先、選択中の接続先へのログインは明示ボタンが対象です。CLI検出・Usage取得済みの表示はログイン成功を保証しません。

Resourcesのサービス別カードが唯一の管理画面です。利用状態・認証・モデル・使用率・アカウント使用枠を同じカードで扱います。モデル能力・ベンチマークもResourcesに置き、右Usageは読み取り専用の簡易表示です。編集フォームは複製せず、画面移動や使用量の自動更新でも未保存入力を保持します。未保存の負荷分散設定は他の設定の保存で消えず、古い利用ON/OFFやOpenCode接続先を上書きしません。

「Resources → 利用するサービス」で既定モデルを保存できます。Codexは公式app-serverの `model/list`（使用量取得とは独立）、Antigravityは `agy models`、OpenCodeは現在の接続先の一覧を取得します。Claudeは公式のモデル別名を選びます（契約での利用可否を確認した一覧ではありません）。全CLIでモデルIDの直接入力・既定設定への復帰が可能です。候補取得だけでは推論や認証・課金方式の変更は行いません。

優先順は「担当別指定 → タスク別指定 → Resourcesの設定 → CLI既定」です。変更は次に起動する工程に反映し、実行中の端末は切り替えません。OpenCodeの接続先プリセットがある場合は、その接続先のモデル制約・既定が適用されます。候補はこのMacのCLIから取得し、SSH先の一覧取得には未対応です。モデル候補と契約の使用量枠を同一視せず、モデル別名の実体・利用可否はCLIと契約に従います。

公式仕様: [Codex model/list](https://learn.chatgpt.com/docs/app-server#list-models-modellist)、[Claudeモデル設定](https://code.claude.com/docs/en/model-config)、[Antigravityモデル一覧](https://antigravity.google/docs/cli/headless/)。

`Resources → 利用するサービス`、または右側使用量の詳細ポップアップから、Codex / Claudeそれぞれの認証状態を確認できます。「CLIを開く」は公式の `codex login` / `claude auth login` を専用対話端末で起動します。ブラウザ認証・コード入力はユーザが行い、このアプリは端末内容を外部ログに保存しません（CLI自身の診断ログは別です）。認証情報の保存は各CLIに任せます。同じMacの同じCLIのエージェント端末が残っている場合は先に終了してください。SSH接続先の認証は別で、この画面では変更しません。状態画面を開くだけでは認証の変更はしません。[Codex公式の認証操作](https://learn.chatgpt.com/docs/auth)

Codex・Claudeの「状態を更新」は認証設定の確認と使用量の再取得をまとめて行います。選択したサービスの認証失敗・通信失敗の待機を解除し、実際の使用量APIで再確認します（操作は30秒間隔）。HTTP 429の待機は解除しません。ログイン済みというCLIの回答だけでは、使用量APIの認証成功とは判定しません。失敗時は前回値と取得時刻・エラーを保持します。Codexのモデル一覧取得が遅延・失敗しても、取得済みの使用量は反映します。APIキー認証ではChatGPTサブスクリプションの上限情報を取得できません。パスワード・トークンの直接編集、自動ログアウトはありません。[Claude公式CLIの認証操作](https://code.claude.com/docs/en/cli-reference)

タスクの反復回数は `各タスク → ゴール → 進め方・作業目安時間 → 最大修正サイクル` で、作業開始前に1〜5回（初期値3回）を指定します。初回を含む修正サイクルの上限で、CLI内部の呼び出し回数や時間切れによる強制終了ではありません。完了には異なるCLIによる2回連続のレビュー合格が必要です。開始後はこの欄を変更せず、上限に達して停止したタスクは追加指示で次のラウンドを開始できます。

レポーターの停止理由はルールの版不一致、確認形式の不正、具体的な未解決事項を区別します。原因解消後に「レポーターから再開」で既存成果を保持してPDF確認と後続レビューを続行できます。

TeX・PDFはタスクの作業場所で生成します。遠隔タスクは登録済みSSH接続先のCLIとTeX環境、ローカルタスクはこのMacを使います。以前のMacビルド設定は読み込み時に移行し、既存の停止タスクにも次のレポーターから適用します。生成場所の切替欄はありません。遠隔側のTeXコマンド・モジュール等は「遠隔システム」の設定・利用手順で指定してください。latexmkがなくても利用可能な同等のエンジン列を使えますが、無許可インストールやMacへの自動切替は行いません。ツール不足は具体的なコマンド名を示して停止します。

遠隔のレポート原稿・生成済みPDFを正本とし、Macへ取得してGUI内にプレビューします。ローカルビルド成果を遠隔レビューへ送り返す工程は不要です。以前転送済みの版があるタスクはその遠隔ディレクトリを継続利用し、そこで再ビルドします。転送が失敗した以前のローカル編集は遠隔側へ自動上書きせず、必要なら内容を照合してください。プレビュー取得の転送上限は5,000ファイル・合計250MB・1ファイル100MBです。Git内部情報・ハーネス管理領域は転送せず、成果物はリンクでなく通常ファイルとしてまとめます。PDFの再生成・執筆ルール・独立レビューは引き続き必須です。

分離済みのローカルレポート保存領域では、以前の画像プレビュー等のファイルリンクが取得先と重なった場合、遠隔ファイルの取得成功後にリンク自体を通常ファイルへ置き換えます。リンク先の内容は変更せず、取得失敗時は既存ファイル／リンクを保持します。親フォルダのリンク・実フォルダとの衝突は引き続き拒否し、エラーに相対ファイル名とMac上の保存先を表示します。一般の作業ファイル取得と旧混在保存領域にはこのリンク置換を適用しません。

### 効率重視の割り当て・並列レビューと統括

#### 完了イベントを受けた統括役の追加配分

主担当方式で分担を有効にすると、計画内の担当が完了した区切りで、保存済み計画の統括判断を行います。初回計画・再計画・途中判断は、時間短縮、サービス負荷の分散、独立検証・別案探索という共通方針を使います。最大同時実行数1の直列作業でも有効です。判断中は未着手の担当を起動せず、既存の読み取り担当は継続します。書き込み担当とは重ねません。待機中のモデル呼び出しや、空きを埋めるだけの仕事は行いません。

統括役は承認済みゴール・現在の研究工程・短い成果要約・残予算を受け取り、既存計画の継続、有用な読み取り専用調査の追加、未着手担当への指示補足から判断します。補足は元の作業指示・達成条件・依存関係・モデルや必須スキルを置き換えず、別の記録として保存します。着手・再試行済みの担当、レポーター、独立レビューや独立照合担当は補足対象にしません。補足先が判断中に変更された場合は適用しません。追加調査は主担当統合の前提として保存し、未検証の完了扱いにはしません。判断と理由、各担当への補足、任意の「分担の目的」は実行計画に表示し、指示書TXTにも含めます。

1ラウンドで最大3判断、追加作業は戦略設定の最大分担数までです。統括の起動予算は見積り合計9,000 tokens以内、ユーザー予算がある場合はその10%以内にも制限します。実測課金の厳密な上限ではなく、新規起動の制御です。既存作業・主担当統合・最終レポート／レビューの見積りを先に確保します。無効な判断、利用枠不足、停止要求では追加を見送り、既存計画とログを保持します。

同じ完了イベントを再開後に重複処理せず、統括が追加した調査から再帰的に判断を増やしません。実作業の失敗は既存の主担当再計画、接続・使用枠の障害は実行復旧へ分けます。途中判断は指示補足・調査追加までで、計画全体の自動置換、実行中作業の切り分け・取消、定期的な停滞のLLM診断は行いません。遠隔タスクの統括判断はMac上の保存済み要約を使い、追加のSSH接続や遠隔実行ロックを占有しません。追加分担そのものは元のタスクの作業環境・設定に従います。

#### コーディング作業の分離実装

コーディングモード、および研究モードのコーディング工程では、初回／主担当再計画に `kind: "isolated-work"` と担当ファイル `ownedFiles` を指定できます。プランナーが独立性と統合コストを考えて選び、常に並列化するわけではありません。既存の同時実行数とCLI選択を使い、Mac・遠隔の双方で各担当にGit worktreeを作ります。遠隔への接続設定・タスク作成でも指定済みの同時実行数を1へ上書きしません。既存タスクの設定値は自動変更しません。

開始条件は、コミット済みで変更のないGitリポジトリのルート、重複しない明示的な担当ファイルです。満たさない場合は変更を勝手にコミット・破棄せず、主担当が準備するか `primary-work` の直列作業へ再計画します。分離領域はファイル競合を避けるためのもので、セキュリティサンドボックスや独立したGPUではありません。共有GPU・MPI・バッチ実験・外部サービスの並列使用をこの機能だけで許可しません。

担当の終了後も自動取り込みはしません。主担当が `workspace_manage` の `snapshot` / `inspect` で実際の差分とテスト根拠を確認し、確認時のダイジェストを添えて `merge` を要求します。担当外変更、リンク、削除、基準コミットの変更、元ファイルとの競合は拒否します。未追跡・無視された生成物も担当範囲を検査するため、ビルド用一時領域はworktree外に分離します。採用しない作業は理由付き `discard` で除外できますが、成果は削除せず元のゴール条件も残ります。未統合の作業がある限り完了判定を通しません。統合記録は正しさの証明ではなく、共有作業場所での回帰テストと独立最終レビューが引き続き必要です。

複数ファイルの統合途中で中断した場合は元ファイルのバックアップと統合意図を保存し、再試行時に元・先双方のハッシュを照合します。後から変更されたファイルは上書きしません。分離成果を使う後続担当の前には、明示的な `primary-work` 統合工程を挟みます。次の分離実装の組を起動する前に、主担当が統合・テストを終えてコミット済みの基準を用意します。HPCモードの既存の数値検証付き統合は別経路のまま維持します。

「会話を切り替える文脈量の目安」は空欄で未指定にできます。未指定の場合、ハーネスは文脈量による会話切り替えを行いません。独立レビューや担当・モデル・権限変更などの切り替え条件、CLI自体のコンテキスト上限は維持します。数値を設定する場合は4,000〜200,000です。既存の設定値は自動では変更しません。

`システム設定 → 実行の基本設定` で新規タスクの既定値として、`割り当て方針 → 効率重視` と最大同時実行数（1〜8）を指定して保存します。プランナーが有用な独立作業と依存関係を判断し、空いている別サービスを優先します。同一サービスの複数起動も可能です。並列数を埋めるための分担は作らず、読み取り専用の調査・検証を並列化し、ファイル編集は主担当に一本化します。

新規インストールの既定値、および効率重視を選んだ際のレビュー方式は「並列レビュー＋統括」です（個別に変更可能）。タスクで許可されたCLIと接続・使用枠を基に、レビュー開始時に利用可能な別サービスの独立担当を確定します。他の判定を見せず、同じ成果物を新規の読み取り専用会話で並列レビューします。全員の有効な判定を受領した後、1担当が全判定の指摘・食い違いを整理し、成果物・証拠を再確認します。統括担当は利用可能なCLIから選び、使用枠不足時は別CLIへ引き継げます。Nサービス＋統括1回（原則N+1起動）を予算予約に反映します。同時実行数がサービス数より小さい場合は分割実行し、上限1では順番に実行します。

統括は独立票の追加ではありません。元の必須条件のfail/unverified、未解決の指摘を合格へ上書きせず、少数意見も残します。単なる多数決や同じ指摘の省略で合格にはしません。「全サービスのクロスレビュー」は従来どおり各サービスが他社の判定を検証する2N回の方式として残します。保存済みの既定値と既存タスクは勝手に書き換えません。`システム設定 → 実行の基本設定 → レビュー方式` で新規タスク用の既定値を変更できます。

一件でも未達・未解決事項が残ればワーカーへ差し戻し、修正・PDF確認後に両段階をやり直します。障害時は他サービスの完了済み判定を保持して再開できます。2サービス未満の場合は待機し、勝手に対象を減らしません。既存タスクは従来の2回レビューを保持し、レビュー開始後の方式変更はできません。遠隔の同時実行数は初期値1で、共有接続と施設の制約を確認した上で増やせます。

### 長い指示と遠隔CLIの起動復旧

Antigravityには指示全文をコマンド引数で渡さず、実行ごとに保存した `instructions.txt` を全文読む短い起動指示を渡します。ローカル・遠隔の両方で、指示・執筆ルール・結果提出方法を省略せず保持し、対話画面も維持します。

遠隔CLIの起動時に `E2BIG` 等の同期エラーが出た場合も、未起動の終了記録を保存して、その実行が所有するロックだけを解除します。復旧用のトークン・ロック情報は `session-control.json` に分離し、旧形式の大きな `launch.json` は遠隔側で上限付きで読み、指示全文をMacへ再転送しません。旧E2BIG障害は、起動直後のエラーログ・同一ホスト・対象ロックの所有者・管理プロセスの終了・Linuxの残存プロセス検査が揃う場合のみ自動復旧します。確認できない場合は従来の手動確認を維持し、推測で終了扱いにはしません。

### タスク画面の見方

タスク内は「概要」「実行」「成果・検証」「レポート」「履歴」の5タブです。概要は目的、実行中の担当、次の作業と前提条件、直近3件の変化に絞り、「できたこと・残っていること」の達成条件一覧は「成果・検証」に集約しています。「目的・条件を確認」で既存のゴール編集・ルール確認、「計画・担当の詳細」で全工程と指示書の全文・TXT書き出しを開けます。

「成果・検証」の表示内容から、達成条件、品質検査、研究台帳、HPC移行・ジョブを切り替えます。PDFは独立した「レポート」タブで、成果物と過去の版を選んで表示します。遠隔タスクではレポート工程完了後に取得・確認したPDFのローカルコピーを表示し、遠隔ファイルのライブ表示ではありません。実行タブのCLI原画面と復旧・引き継ぎ操作は維持しています。履歴には工程別の記録を表示し、概要の変化一覧を重ねて表示しません。報告を開くと冒頭の抜粋は隠れ、本文を一度だけ表示します。

通常の下部欄は追加指示・開始・保存だけに絞っています。作業範囲、担当CLI・モデル、計画承認待ちの変更は上部の「担当・確認設定…」で行います。同じ下書きを共有するため画面を往復しても入力は保持し、移動だけでは保存・実行しません。「その他の操作」の折り畳みはなくし、「再開／一時停止」「実行戦略」「担当・確認設定」を直接表示します。実行戦略は主担当方式のみ、やり直し・削除は停止中のみ、遠隔環境の復旧は停止した遠隔タスクのみ表示します。遠隔Codexの権限は「作業場所・実行設定」、担当・スキルの配置修復は「計画・担当の詳細」、レポート再生成は「レポート」へ配置しています。確認待ちで停止している場合は、回答欄と合格条件の変更操作を停止理由の直下に表示します。既存設定・承認範囲・保存された履歴は変更しません。

本作業をまだ開始していないタスクでは、上部の「開始時のCLI…」で最初の工程に使うCLI・モデルと、使用不可の場合に代替CLIを許可するかを変更できます。ゴール承認待ち・キュー待ちなどの停止中に保存でき、ゴール案作成の実行中は変更できません。AIによるゴール案作成のCLI、ゴール・権限、後続の専門担当・レビューは変更しません。保存自体は実行命令ではなく、次の開始時に既存の接続・使用枠・モデル条件を確認して反映します。「既存の担当設定に従う」でこの指定を解除できます。本作業の担当を一度でも起動した後は、既存の引き継ぎ・担当変更操作を使います。

概要は保存済み情報の読み取り専用表示で、追加のAI呼び出しや実行制御の変更はありません。「作業終了」はゴールの合格ではありません。「合格記録あり」は表示された評価時点の判定であり、最新ファイルのハッシュ再確認や全レビューの合格を保証しません。ゴール・作業回・修正サイクルの変更や評価後の書き込みが記録されている場合は再確認扱いとし、現在の別担当の不合格を多数決で消しません。

### その他の境界（実行仕様）

- 初回は4工程、反復時は選択した作業に応じた工程を直列に割り当てます。完了後の端末は画面・ログの閲覧専用です。自由な工程編集や自動の無限改善ループは設けていません。
- Codexは公式ローカルAPI、ClaudeはCLI自身が使う使用量エンドポイントから、起動時・5分間隔・手動更新時に読み取り専用で取得します（モデル呼び出しはしません）。Claudeの認証は保存済みのKeychainまたはCLI認証ファイルを利用し、認証情報をログやアプリ設定に保存しません。認証切れの場合はClaude Codeでログインを更新してから再取得してください。Claudeの取得先は公開安定APIではないため、仕様変更時には対応が必要です。取得失敗時は前回値・更新時刻とエラーを表示します。その他のCLIは取得可能な値のみを表示し、取得不能な場合は任意設定のソフト上限または `unknown` です。
- 新しいPTY実行ではTUIの文字列からトークン数や内部サブエージェント数を推測しません。契約使用枠の取得は継続し、実行単位の未取得値はunknownです。
- Codex・Claude・OpenCodeの自動引継ぎはネイティブフックと最終マーカーを利用します。CLIのフック禁止ポリシー・認証切れ・明示的な承認必須設定・不正な最終回答などは別途対応が必要です。Codexはこのアプリから起動したセッションに限り `notify` を引継ぎフックに指定します（通常のCLI起動用の保存設定は変更しません）。Geminiの同等のネイティブ完了フックは未対応です。
- 遠隔システム登録・SSH接続共有・ユーザー記述の利用手順に対応しています。tmuxがある遠隔環境ではCLIを保持し、SSH再接続後に同じ工程へ戻れます。
- 主担当方式ではPlannerが可変数の作業単位を生成し、読取専用工程を並列化できます。同一ファイルを複数の書き込み担当が同時編集する構成にはしていません。

正本のMVP仕様は [docs/SPECIFICATION.md](SPECIFICATION.md) を参照してください。

## アプリの診断ログ

起動時から `~/Library/Application Support/agent-harness/logs/application.log` に診断ログを自動保存します。起動・終了、メイン処理の警告・例外、画面側の警告・エラー・応答停止・プロセス終了、タスク／担当の状態遷移を記録します。30秒ごとにメモリ使用量と実行状態を記録し、`session.json` で前回の正常終了も確認します。再起動してもログは残り、1ファイル最大2 MiB、過去4世代を含め約10 MiB以内で循環します。連続エラーは毎秒100件を上限として省略件数を残します。

診断ログへCLIの全出力、ユーザーの入力、認証設定を丸ごとコピーすることはしません。エラーメッセージに含まれる一般的な認証キー・パスワード・URLのクエリはマスクしますが、自由文の機密情報を完全には判別できないため、外部へ共有する前に内容を確認してください。ファイルは所有者だけが読み書きできる権限で保存します。既存の担当別作業ログは引き続きレポートフォルダの `logs` に保存します。

OSによる強制終了（SIGKILL）、電源断、Nodeの例外処理を通らないネイティブ障害では、終了理由そのものを書き残せない場合があります。最後の稼働記録と次回の `previous-session-unclosed` を手掛かりに、macOSの診断記録と合わせて調べます。「正常終了の記録なし」は終了原因の断定ではありません。ログ保存に失敗しても作業処理は中断せず、標準エラーに警告します。

## レポートの前提確認で停止した場合

PDFファイルの生成・更新確認と、内容／文献／執筆ルールの合格は別に表示します。一次資料・異なるAIによる文献照合・実作業の不足がレポーターの正しい版の完了通知に残っている場合、単純なレポーター再実行ではなく、主担当の再計画をレポーターの前に挿入します。自律反復が有効で上限内なら自動で行い、既存の停止タスクでも「不足する確認を再計画して続行」から同じ復旧経路を使えます。

完了済みの前工程とファイル・ログを保持し、不足する担当の作業→統合→レポーター→最終独立レビューの順に進めます。後続レビューが未実施であること自体はレポーターの未完了条件にしませんが、必要な一次資料・二重照合を省略したり合格扱いしたりはしません。再計画は同一ラウンド・ゴール版で最大2回、既存の計画改訂上限・予算・権限・終了確認も適用します。認証・SSH・ツール不足やユーザー承認待ちは、自動再計画では解消した扱いにしません。

研究の再作業上限で残課題の報告へ移る場合も、残る工程が論文執筆だけなら省略せず、既存の結果と留保から論文を作成します。旧版がその工程を省略し、必須の論文PDF不足で停止したタスクでは「論文執筆から再開」と表示します。同じラウンド・工程IDで執筆→PDF生成→独立レビューへ復帰し、実験・履歴・承認条件は保持します。アプリ起動だけではタスクを再実行しません。未確認の研究条件を執筆担当へ繰り返し差し戻したり、事後登録を実験前の固定と扱ったりはせず、最終判定まで未確認事項を残します。PDF不足の表示には、取得済みTeXログの最初のビルドエラーも併記します。

仕上げへ移行した後は、執筆担当が研究全体の未達を`needs-work`として返しても、前工程と執筆が終了していれば残課題として保存し、同じ自己確認を再起動せずPDF確認・独立レビューへ引き継ぎます。仕上げへの移行は一方向で、再試行上限をリセットしません。実際の環境障害、終了未確認のCLI、未着手の前提工程、ユーザー判断待ちはこの経路で迂回しません。旧版でこの途中に差し戻し上限停止したタスクは「残課題を記録して仕上げへ」から同じラウンド内で再開できます。未達が残れば「作業終了・残課題あり」となり、成功や全体合格とは区別します。

仕上げ通知では文章・組版・PDF確認の不備（`concerns`）と、科学的根拠・原典・実験の不足（`prerequisites`）を分離します。後者は主担当へ戻し、未確認のまま合格にはしません。ローカルのPDF確認は、TeX recorder（`.fls`）の入力・図・参考文献・PDFのハッシュ、ゴール版、執筆ルール版がすべて同じ場合だけ、組版・全ページ確認の証跡を再利用できます。変更、不明な依存、未登録の文書、遠隔実行は従来どおり再確認します。科学的な合格や最終独立レビューはこの再利用の対象外です。

取得不能が続く場合は文献名、版、不足する項目、試した取得先と必要な資料を具体化して停止します。「追加資料・取得方法を入力」から既存の追加指示欄へ移動し、「修正・続行」で資料や方針を渡せます。URL認証・CAPTCHAの回避や未確認事項の合格化は行いません。

## 論文解説モード（Beamer教材）

Dispatchで作業場所を確定し、作業モードから「論文解説モード」を選びます。「論文PDFを追加…」で主論文・補足資料を選択し、必要ならGitリポジトリ等の参考HTTP(S) URL、想定読者・既知の知識、理解したい点、日本語/英語を指定します。PDFは1件20MB、合計100MB、最大10件。先頭が主論文で、順序は変更できます。元ファイルを変更せず、作業場所のアプリ専用ディレクトリに保存します。遠隔の場合は既存のSSH接続で転送し、ハッシュが変わった入力を自動上書きしません。URL登録はコード実行・インストールの許可ではありません。

「AIでゴール案を作成」で原論文に基づく背景・前提知識・提案・実験・限界の説明項目と推奨レベルを提案します。ゴール画面の「どこから説明するか」で、各項目を「既知／復習／基礎から／詳しく」に変更し、足りない説明項目を追加して承認してください。承認前は読み取りのみで、教材制作は始まりません。AIによる再提案でも同じIDのユーザー選択と読者設定は保持されます。

主成果物はreport.tex/report.pdfのBeamer教材です。通常のIPSJ報告書を追加生成しません。発表時間・ページ数の上限はなく100ページ以上も許容しますが、既存の実行予算・試行上限は維持します。主担当が有用な調査・図解案・読者批評を分担し、原典忠実性と読者の理解障害を独立評価して改善します。最終仕上げ・独立レビューは従来のゲートを通ります。意味の正しさや人間の理解を機械検査のみで合格扱いしません。

「システム設定 → スキル管理」で lesson-foundations（背景・前提）、lesson-storyboard（絵コンテ・図解・Beamer）、lesson-reader-review（読者/原典レビュー）を編集できます。既存の文献・表現・検証ルールは共通利用します。変更したスキルは試験中に戻るため、検証後に採用してください。新規タスクは採用済みの3スキルを保存し、進行中タスクへ変更を黙って混ぜません。

テンプレートはLuaLaTeX・16:9。同梱の `node check-lesson.cjs report.tex` はフレームID、参照・組版警告を確認する補助で、意味・出典・数値・全ページの表示確認は別に必要です。レポート画面の「ここがわからない」「具体例を追加」「式を順に説明」「図解して」は追加指示欄へ文章を入れます。対象ページ・見出しを記入し、内容を確認して送信してください（クリックだけでは再実行しません）。

開発検証：`node --test dist/core/paper-lesson.test.js`、`npm run test:layout -- --lesson-only`、`node scripts/smoke-lesson.cjs`。最後はMacTeXとPopplerを使い、テンプレートだけをビルド・描画します。実論文の教材品質は、その論文を使った制作・レビューで別途確認します。
