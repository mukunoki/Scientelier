# 大規模コード移行・GPU化モード

## 利用方法

1. Dispatchで作業場所を確定し「大規模コード移行・GPU化モード」を選ぶ。
2. 対象版、移行方式、数値条件、GPU・MPI構成、性能目標をゴールとして承認する。
3. タスクの「移行・検証・ジョブ」でGPU時間・ノード時間・投入ジョブ数・保存量の上限を設定する。空欄は無指定。
4. 主担当が移行単位と検証ケースを登録し、実装・比較・ジョブ投入を進める。GUIから単位を手動設定することもできる。
5. 各単位の全ケースが合格し、ジョブ状態と分離作業の統合が解決してから、レポートと既存の独立レビューへ進む。

作業ルールは「システム設定 → 作業・執筆ルール → モード別」で編集する。研究モードの4工程と他モードの権限は変更しない。既存タスクは保存済みルールを保持する。HPC管理機能はこのモードのタスクだけに提供する。

## 実装した管理機能

### 移行単位・数値検証

単位ID、対象ファイル、依存単位、数値条件の根拠とケースを永続化する。CPU基準、CPU再現、移行版単体、統合の4段階を必須にし、MPI構成・性能条件などはケースとして追加する。未検証・差戻し・再検証待ち・依存検証待ち・統合検証済を区別する。

比較ファイルは values の下に変数名と数値配列を持つJSON。比較は「絶対差 ≤ 絶対許容差 ＋ 相対許容差 × 基準値の絶対値」。変数集合・配列長の相違、空配列、NaN/Inf、計算中のオーバーフローも拒否する。異なる許容差の変数やMPI配置は別ケースにする。0は完全一致であり、汎用の科学的許容差ではない。

ケースごとにコード、依存単位、基準・結果、環境マニフェスト、検証スクリプトをハッシュで対応付ける。内容が変わると合格を無効化し、依存先も再検証対象にする。最初の比較で基準を固定し、AIが通過目的で基準や許容差を書き換えられないようにする。ユーザーによる単位定義の改訂は過去の合格を無効化する。

主担当が ready/report-ready と報告しても、台帳なし・ケース未合格・未照合ジョブ・未統合作業があれば、既存の自律反復上限内で作業へ差し戻す。最終完了時にも再確認する。ターミナルの終了を数値合格とはみなさない。

### 計算ジョブと復旧

スケジューラは固定しない。エージェントはユーザー登録のプレーンテキスト手順から、短い投入コマンドと照合コマンドを組み立てる。コマンドの標準出力は、ジョブIDと状態を持つJSONに整える。秘密情報は含めない。

- 投入前に一意の実行ID、再試行キー、コード・入力・環境のハッシュ、予約資源量、出力先を永続化する。
- 同じキーは以前のジョブを返し、二重投入しない。コードやコマンドが変わった同じキーは拒否する。
- 投入応答が途切れても不明状態と予約量を保持する。新しいキーで同じ未解決ジョブを再投入しない。
- 照合コマンドは保存されたものを使用する。GUIの「状態を照合」、または担当の管理操作から確認できる。
- HARNESS_RUN_ID、HARNESS_JOB_ID、HARNESS_OUTPUT_DIRをコマンドの環境変数として渡す。投入時のジョブ名等へ実行IDを含め、ID応答が失われても検索できる照合方法を設計する。
- queued/running/succeeded/failed/unknownを区別し、成功には計算ジョブの終了コード0を要求する。実績値が報告されるまでは予約見積もりを計上する。

投入・照合コマンドには20秒の制限がある。これはスケジューラとの短い通信処理の制限であり、計算ジョブ自体を時間切れでキャンセルするものではない。長時間のコンパイルや計算を投入コマンドの前景で実行してはいけない。照合失敗は成功にも再投入にも変換しない。

予算は新規投入の着手制御であり、実機の強制的な使用量制限ではない。上限を下げても既存ジョブを殺さない。トークン予算とは独立して管理する。

### 分離した並列実装

主担当の実行計画は、HPCモードに限り isolated-work と ownedFiles を指定できる。専門調査の読み取り専用指定は従来どおりで、暗黙に書込み担当へ変わらない。

- Gitリポジトリのルート、コミット済みの基準、重複しない明示的なファイル範囲が必要。未保存・未コミットの変更を自動で捨てたりコミットしたりしない。条件を満たせない場合は primary-work の直列計画を使う。
- 担当ごとにdetached worktreeを作り、同時に起動する。空いた枠には依存条件を満たす次の予定作業を入れる。共有作業場所への書込み工程は全担当を待って排他的に実行する。
- 担当範囲外の変更、基準コミット変更、共有側の変更競合、未完了ジョブ、CPU基準・再現・単体の証拠不足を検出すると自動統合しない。
- 統合前の不備は主担当へ伝える。主担当は保存済みworktreeで証拠を修復し、同じ検証付き統合操作を再実行できる。
- 統合しても共有側の合格は引き継がず、統合テストを要求する。新規ファイルも明示的に所有範囲へ含める。自動削除は行わない。
- GUIで差分・場所・担当ターミナルを開ける。停止後の「成果を保持して割当解除」はファイルを残して将来の割当てから外す。
- 遠隔でも同じ処理を実行し、分離担当の実行ロックを分ける。通常モードの遠隔直列実行は維持する。

worktreeは編集衝突を避ける仕組みで、OSのセキュリティ境界ではない。CLIをfull accessで動かす場合、モデルの役割指示だけで他の場所へのアクセスを物理的に防ぐことはできない。

複数ファイルの統合前にバックアップと統合予定を保存する。途中でアプリやホストが落ちた場合、再試行時のハッシュ不一致で停止し、変更を盲目的に上書きしない。部分統合からの完全自動ロールバックは行わない。保存済みバックアップと差分を確認して復旧する。

### 専用画面と保存場所

タスク内の「移行・検証・ジョブ」に、単位・ケースの合否、最大誤差と不一致数、証拠履歴、ジョブ状態・観測内容、資源予約／実績、worktreeと差分を表示する。「最新の検証状態を確認」で外部変更も再検査する。編集途中の入力はタスク画面の再描画でも保持する。

台帳は作業場所の .agent-harness/<task ID>/hpc/ledger.json。遠隔タスクは遠隔の台帳が正本で、GUIからは既存の持続SSH接続で操作する。接続がなければ不明・エラーとして表示し、ローカルの空台帳で代用しない。ジョブ出力、worktree、統合前バックアップも同じ管理ディレクトリ内に置く。

更新は排他ロックと一時ファイルの置換で行う。ロック所有プロセスが終了していた場合、GUIの「台帳ロックを復旧」で同じホストのPIDを確認して解除できる。時間が経ったという理由だけでは解除しない。HPC管理操作はCodex/Claude/OpenCodeには実行単位のMCP、Antigravityには同じ権限付きエンジンのコマンドとして提供する。

## 制限と検証の境界

- 数値比較は提出ファイルに対する検証であり、実際にそのコードで計算した証明ではない。実行コマンド・スケジューラ観測・測定ログを残し、独立レビューで照合する。
- Fortran解析器、実行状態の自動抽出、物理量・性能目標の汎用判定器は含まない。必要な再現テスト・エクスポーターは担当が実装する。
- 個々の数値比較・証拠ファイルは32MB以下に分割する。大きなダンプは必要な部分を抽出し、管理対象へ巨大ファイル全体をそのまま渡さない。
- 現時点では500単位、各単位100ケース／500検証履歴、1000ジョブを上限にする。巨大な移行は複数の承認可能なタスク・バッチへ分ける。
- ジョブ照合はエージェントまたはGUIの明示操作で実行する。無条件にスケジューラを頻繁にポーリングする常駐監視は追加していない。
- 実機のGPU・MPI検証をテスト用の擬似スケジューラで代用したとは扱わない。利用する各スパコンで最初に小ケースを通す。

## 論文との関係

[Validation-Centric AI-Assisted GPU Porting of a 250,000+ Line Legacy Weather Simulation Code](https://arxiv.org/abs/2608.13122)のCPU再現テストを先に検証する方法と、高コストな入力採取の失敗をまとめて修復する考え方を参考にした。同論文の実証は単一ノード・選択されたFortran/OpenACC計算ケースであり、C++移行や複数ノードMPIへの対応は本アプリ側の拡張である。論文固有の速度向上率や許容差をデフォルトの合格値にはしない。
